# Codex Hook 信号契约

> 本文是 bridgeforge-codex 的 Hook 信号参考。`[clarify]` 和 `[focus]` 是提醒，不是用户命令、权限或自动阻断。根 `AGENTS.md` 只保留一行响应红线，完整条件以本文为准。

## `[clarify]`

目的：防止新的、大而模糊的需求在目标、范围或验收尚未收敛时直接进入实现。

收到信号后：

1. 先判断当前消息是否真是新的大需求。
2. 琐碎修改、原任务续接或细节完整时忽略信号并直接执行。
3. 只有缺失信息会实质改变实现或验收时，才说明当前理解、可选路线、推荐路线和理由，并只问一个最关键问题。
4. 能从本地事实安全确定的内容先自行核验，不把可查事实交回用户。
5. 连续确认每满 3 个问题必须暂停并总结已经确定、仍待确定和已排除的内容。
6. 超过 6 个问题仍未收敛时，必须改写成需求或验收草案，让用户核对整体，而不是继续逐题追问。
7. 目标、非目标、触发条件、验收、合理假设和剩余风险已经说清时必须停止追问。

需要落盘需求并完成用户试用闭环的大需求进入 `$develop`；评估或咨询类任务直接给结论和风险。

信号不得被解释为“所有请求都必须先走确认卡”或“看到信号就停止”。

## `[focus]`

目的：提醒 Agent 检查是否在长对话中无意偏离原任务。

收到信号后：

1. 对照任务锚检查当前工作与用户最新意图。
2. 用户明确切换任务、补充范围或沿原问题正当深入时忽略信号。
3. 小前置问题内联解决后返回主线；足够大的独立阻塞使用 `$spinoff`；无关支线使用 `$todo` 记录，不在当前任务展开。
4. 方案替换或范围变化时必须说明原方案、现方案和原因；有证据时一并给出。
5. 顺手修改用户未点名的内容时，必须说明修改范围和理由。

信号不得阻止用户主动改变主线，也不得把历史任务锚置于用户最新消息之上。

## 为什么不把完整规则常驻在 AGENTS

Hook 已经在相关事件中注入信号。根文件只需要说明信号的权限边界，完整分类和调试步骤按需读取即可。这样避免“长规则常驻 + 信号再次提醒”的双重上下文成本。

## 调试

调试时分别验证两件事：

1. 信号是否在正确事件和输入下产生。
2. Agent 是否按语义正确响应。

每次记录 hook event、matcher、输入类别、是否发出信号、返回码和 Agent 行为。禁止用“Hook 打印了文字”代替行为验证，也禁止用一次正确响应证明长期稳定。
