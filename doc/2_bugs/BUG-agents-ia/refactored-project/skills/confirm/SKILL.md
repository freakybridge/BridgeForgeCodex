# confirm — 统一需求确认

## 定位与边界

作为高级开发流程的开工确认单：先核验真实载体，再逐项确认需求。用户最终确认完整卡片之前，禁止写需求文档、改代码或启动高成本 agent。

## 输入

- 用户的原始目标、点名载体、已知约束和验收线索。
- 本轮已有确认卡（如有），用于判断目标、范围、约束和验收是否仍匹配。
- 被 `develop`、`debate` 或 `collab` 调用时的交接目标。

## 核心流程

### 0. 规模与预算硬闸

本节是 S/M/L 规模、时间 / token / agent / 验证预算及验证轮次口径的唯一事实源。其他 Skill 只能读取本节或确认卡结果，禁止复制具体阈值、预算数值与计算规则。

1. 在启动访谈或高成本 agent 前，按“逻辑改动”而非原始文件数给出暂定规模；模板镜像、版本、CHANGELOG 和 manifest 等机械传播文件不单独抬高规模：
   - **S**：单一已知问题、方案基本明确、可逆，不涉及新架构、数据迁移或高风险业务规则。
   - **M**：跨模块或存在少量实现分叉，但边界、接口和验收可在短确认后锁定。
   - **L**：新功能、架构变更、数据迁移、高风险交易 / 安全规则，或存在多个会改变结果的未知项。
2. 给出并写入预算：S 默认 `20 分钟 / 8k 新增 token（估算）/ 0 个子 agent / 1 次验证 + 1 次修复重测`；M 默认 `45 分钟 / 20k 新增 token（估算）/ 最多 1 个子 agent / 最多 2 次验证`；L 必须在开工前由用户确认时间、token、agent 和验证轮次预算。预算是任务上限，不是乐观最低值；必须一次纳入已知验收面、合理修复重测和环境重试缓冲，禁止故意压低后逐轮追加。
3. 平台没有可靠 token 计量器时，必须标记“token 未实测”，并以 agent 数、验证轮次和范围增长作为代理闸；禁止伪报精确 token 消耗。
4. S 级最多确认一个真正会改变实现或验收的问题；事实已经充分时直接展示确认摘要。M/L 仍按单题逐项确认。
5. 新证据导致升档，或预计将超过时间、token、agent、验证轮次任一预算时，必须先停止并只问用户选择“扩大预算”或“缩小范围”；不得静默扩张流程。

验证轮次统一口径：一轮是一次“实现或实质修复完成后，执行预定验收集并取得完整结果”的闭环；同一验收集可包含多条命令。工具中断、权限重试、日志丢失、输出通道故障，以及代码未变时补跑同一验收集，都计入时间 / token 成本，但不单独消耗验证轮次。只有根据完整失败结果再次修改实现或验收契约后重新验证，才进入下一轮。等待 agent、重复审计或重复测试仍计入时间 / token 成本；是否消耗验证轮次按本口径判断，禁止视为免费开销。

### 1. 核验事实

1. 用户点名文件、表格、页面、报表、接口、数据库、业务流程或历史记录时，先只读真实载体及直接关联的读写 / 输出入口。
2. 表格至少核验 sheet、表头、关键日期列、公式或格式和代表性历史行；页面、报表与接口至少核验当前字段、触发入口和输出语义。
3. 输出“已核实事实 / 未核实事实”。此阶段禁止展示确认卡或实施方案。
4. 载体不可访问时报告卡点；用户明确要求概念讨论时可以继续，但相关结论必须标为假设。

### 2. 逐项确认

1. 从真实事实中识别会改变实现或验收的要点，例如目标与范围、记录单位、用户动作与时点、字段映射、状态与例外、历史语义、非目标和验收标准。
2. 每轮只问一个要点，并使用具体、互斥、会改变实现的选择题：

```text
问题：{一个具体开发要点}
A. {基于已核实事实的选项}
B. {互斥选项}
C. {可选的第三条合理路径}
D. 其他：{用户补充真实需求}
```

3. 用户选“其他”时，把补充整理为当前要点的新选项，再单题确认；不得直接当作最终结论。
4. 用户暂不确定时，单题确认该点是阻塞、采用临时默认还是移出范围；影响用户行为、数据、接口或验收的默认规则必须再次确认。
5. 所有实际要点都确认、明确待定处理或被排除后，才进入完整确认卡。

### 3. 确认并落盘

1. 展示包含以下内容的完整确认卡：目标、不做、任务规模与判定依据、时间 / token / agent / 验证预算、超预算停止点、已核实事实、已确认业务规则、数据映射、拟修改、验收、合理假设与风险、自动化边界。
2. 只问以下一题，并结束当前回合：

```text
问题：以上是否准确表达你的真实开发需求？
A. 准确，写入需求卡并继续
B. 有一项不准确，继续逐项确认
C. 暂不写入，只保留讨论结论
```

3. 只有用户明确选择 A 或给出唯一、无条件对应 A 的回答，才按 `doc/README.md` 的 `delivery_layout` 写入：`flat` 为 `doc/1_delivery/<topic>/requirements_YYYY-MM-DD_<slug>.md`，`milestone` 为 `doc/1_delivery/<M>/<topic>/requirements_YYYY-MM-DD_<slug>.md`。无有效声明时停止要求用户选择；同步 `doc/README.md`。
4. 需求卡必须包含上述确认内容、原始需求摘要、调用来源、后续交接目标以及实施 / 验证记录占位。

### 4. 交接

- 被高级 skill 调用时，返回确认卡路径，由调用方继续，不重复访谈。
- 用户直接调用时，落盘后只问一题选择 `develop`、`debate` 或 `collab`；用户选择后交接。

## 输出与收据

- 事实核验阶段：已核实与未核实事实。
- 落盘阶段：确认卡路径、状态、S/M/L 规模、预算及 `doc/README.md` 索引更新。
- 交接阶段：目标高级 skill 和确认卡路径。

## 停止条件

- 每个选择题发出后立即结束当前回合，等待用户回答。
- 点名载体不可访问且事实会影响需求时，报告卡点并停止确认该项。
- 确认卡任务不匹配或已过时，视同无卡，重新进入本流程。
- 规模升档或预算预计超限时，报告已用 / 剩余预算和升档原因后停止。

## 禁止事项

- 禁止一轮提出多个开发问题或附带问题清单。
- 禁止以抽象技术方案代替业务规则确认。
- 禁止最终确认前写需求卡、改代码或启动高成本 agent。
- 禁止高级 skill 绕过本流程自行补问后继续。
- 禁止只按改动文件数判定规模，或把机械镜像与发布元数据当成业务复杂度。
- 禁止未记录规模和预算就把确认卡交给 `develop`。
- 禁止自动 `git add`、commit 或 push。
