# develop — 大需求交付流水线

## 定位与边界

先执行规模与预算硬闸，再按 S/M/L 选择成本匹配的交付路径。需求访谈由 `confirm` 完成；本 skill 不重复确认业务细节。单文件小修、文案微调、明确 bug 的一次性修复、纯咨询或只读方案必须走 S 级直接路径，不得启动完整流水线。

## 输入

- M/L 级需要与当前目标、范围、约束、验收和预算匹配的 `confirm` 需求卡；S 级不得为进入流程而补卡。
- `$ARGUMENTS`：用户的大需求描述。
- 项目真实代码、文档规范、测试入口和 Git 状态。

## 核心流程

### 1. 规模与开工硬闸

1. 在调用 `confirm` 或任何子 agent 前，由主对话按 `confirm` 的逻辑改动口径判定 S/M/L；机械镜像、版本、CHANGELOG 和 manifest 不单独抬高规模，并输出规模、依据和预算收据。
2. **S 级直接路径**：预算固定为 `20 分钟 / 8k 新增 token（估算）/ 0 个子 agent / 1 次验证 + 1 次修复重测`。禁止创建需求卡、调用 `confirm` 或启动 discovery / implementation / review agent；主对话直接实施并做针对性验证，完成后直接交付收据，不进入 Step 2-6。用户或项目硬规则明确要求需求卡 / 独立审计时，必须升为 M 并触发预算升级闸。
3. **M 级精简路径**：默认预算为 `45 分钟 / 20k 新增 token（估算）/ 最多 1 个子 agent / 最多 2 次验证`。必须使用含规模预算的有效确认卡；主对话默认完成 discovery 和实现，只在缺少确定性替代或项目硬规则要求时使用一次子 agent。
4. **L 级完整路径**：必须先由用户确认时间、token、agent 和验证轮次预算，再使用完整确认卡及后续分段 agent 流程。预算必须按现实上限一次覆盖已知验收面、合理修复重测和环境重试缓冲；禁止用乐观最低值制造逐轮追加确认。
5. 平台无可靠 token 计量器时标记“token 未实测”，用 agent 数、验证轮次和范围增长做代理闸；禁止伪报精确 token 消耗。
6. M/L 没有匹配、未过时且包含规模预算的确认卡时调用 `confirm`，在它返回前禁止开发。
7. 读取 M/L 有效卡，不重复访谈，只问：

```text
问题：是否按这份已确认需求开始开发？
A. 是，开始落盘并实现
B. 否，回到 confirm 修正需求
C. 暂不实现
```

8. 只有用户明确选择 A 或给出唯一对应 A 的无条件回答，才进入实施。

### 1.1 预算升级闸

- 每次准备扩大范围、启动子 agent、运行全量测试或进入第二次修复前，核对剩余预算。
- 预计超过时间、token、agent 或验证轮次预算，或事实导致规模升档时，必须停止并只问用户选择扩大预算或缩小范围。
- 一轮验证是一次“实现或实质修复完成后，执行预定验收集并取得完整结果”的闭环；同一验收集的多条命令仍是一轮。
- 工具中断、权限重试、日志丢失、输出通道故障，以及代码未变时补跑同一验收集，不单独消耗验证轮次；它们仍计入时间 / token 成本。
- 只有根据完整失败结果再次修改实现或验收契约后重新验证，才进入下一轮。
- 禁止把等待 agent、重复审计或重复测试视为免费时间 / token 开销。

### 2. 完善需求包

仅 M/L 进入本阶段。

1. 在确认卡中补充实施计划、实施记录和验证记录，不重建第二份需求。
2. 项目级长期约束更新 `doc/0_architecture/`；单 feature 保持在确认卡所属的 `doc/1_delivery/` topic；新 Bug 写入 `doc/2_bugs/`。不得再创建全局 plan 或 pending 文档。
3. 需求包至少保留背景与目标、非目标、用户可见行为、约束与风险、验收、暂缓项和实施假设。
4. 新增、删除或重命名 `doc/**.md` 时同步 `doc/README.md`。
5. 此后自动推进，只在卡点、高风险或完成时打断用户。

### 3. 拆解与实现

1. M 级默认由主对话单线 discovery 与实现；只有缺少确定性替代或项目硬规则要求时，才在总预算内使用一次匹配职责的子 agent。
2. L 级把 read-only discovery 显式分派给 `light-explorer`，让它读取代码和文档并返回单一事实源、既有模式和风险收据；主 agent 据此决策。
3. L 级实现阶段显式分派给 `implementation-worker`。并行前定义接口和文件边界；同组 agent 禁止改同一文件。每个任务必须携带整体目标、需求卡路径、验收、边界和接口。
4. 子任务最多重试 1 次；再次失败即报告卡点，不循环。
5. L 级需要并行时复用 `collab` 的执行约束，但不得重新走其用户确认闸。

### 4. 同步事实与文档

- 已确认范围内的实现细节、事实补全和验证状态直接更新需求包或设计文档。
- 任何用户行为、业务规则、接口、范围或验收变化都必须暂停，以单题选择确认；不得用文档追认未确认变化。
- 完成后更新实施状态、变更记录、每项验收状态及相关设计 / rules。

### 5. 独立验证

1. 运行与规模匹配的 lint、类型检查、单测、集成测试或手工验证脚本；S/M 禁止无依据升级为全量测试。
2. M 级只有在用户 / 项目硬规则要求，或缺少覆盖关键风险的确定性测试时，才在 agent 预算内分派一次 `review-auditor`。
3. L 级把 delivery review 显式分派给 `review-auditor`，向它提供需求卡、验收、改动文件，并要求独立读取真实文件和 `git diff`，核对遗漏、串联、回归和文档。
4. 规则和可执行测试优先于 LLM review；平台无必需的独立 agent 能力时，明确标注未完成该验证。

### 6. 试用闭环

1. 交付改动、需求卡、验证收据、用户试用主路径和剩余风险。
2. 属于当前需求的小 bug 直接修并更新同一需求包；独立 Bug 建立 `doc/2_bugs/BUG-<id>-<topic>.md`；新范围进入新的 `confirm` / `develop`。
3. 同一症状修复失败两次，停止并按项目鬼打墙规则升级。

## 输出与收据

- M/L 的需求卡与相关设计文档路径；S 级明确记录“按规模闸免需求卡”。
- 实际改动文件及用户可见行为。
- 每条验证命令、断言、覆盖场景和独立 review 结论。
- 实际规模、预算使用状态、是否升档及原因。
- 未通过、未验证项及试用主路径。

## 停止条件

- M/L 开工选择题、需求边界变化或高风险操作出现时，结束当前回合等待用户。
- 缺少关键输入、子任务连续两次失败或验证无法继续时，报告卡点。
- 独立验证不可用时允许交付，但必须明确标为未完成。
- 规模升档或预计超预算时必须在继续前获得用户单题确认。

## 禁止事项

- 禁止 M/L 无有效规模预算确认卡开发或重复 `confirm` 访谈；S 级禁止为了流程完整而创建确认卡。
- 禁止 M/L 在用户确认开工前改代码或配置；用户明确要求执行即视为 S 级直接路径的开工授权。
- 禁止 Step 2 后把普通实现细节反复交回用户决定。
- 禁止用主 agent 总结代替独立读取真实 diff。
- 禁止遗漏 `doc/README.md` 索引同步。
- 禁止 S/M 任务默认启动完整三段 agent 流程。
- 禁止超过预算后才补报，或把 agent 等待和重复验证排除在预算外。
- 禁止自动 `git add`、commit 或 push。
