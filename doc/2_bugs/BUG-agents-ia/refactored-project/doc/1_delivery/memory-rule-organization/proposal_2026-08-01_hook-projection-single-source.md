# Hook 投影单一源建议

## 结论

BridgeForge 的 `templates/codex/hooks/` 应是通用 hook 实现的唯一源码；下游项目
保留同名文件仅作为运行投影，不得维护内容分叉。用户级目录不承担这些 hook 的
运行职责，也不应通过绝对路径被下游项目调用。

## 已核对的三个 hook

| Hook | 上游模板能力 | 建议 |
|---|---|---|
| `memory_dup_check.py` | 递归扫描分类 memory，并以相对路径报告候选重复项。 | 维持模板实现为唯一源码；下游更新时覆盖旧的扁平扫描实现。 |
| `memory_lint.py` | 递归校验 memory 索引，覆盖热区与冷区，并支持显式的分类整理计划。 | 维持模板实现为唯一源码；下游不得保留旧的扁平索引实现。 |
| `rule_size_check.py` | 同时提供编辑后的软提醒与提交前的 staged-content 硬检查。 | 维持模板实现为唯一源码；文案统一指向架构文档或所属 delivery topic。 |

## 运行边界

1. 上游模板负责版本化、审阅和发布；它不是下游运行时目录。
2. 下游 `.codex/hooks/` 负责运行时执行；对应注册仍留在下游
   `.codex/settings.json` 与项目 `.githooks/pre-commit`。
3. 用户级目录只负责分发 BridgeForge skill，不注册这三个项目行为 hook。
4. 禁止下游修改同名投影；有通用改进时先修改上游模板，再经受管更新同步到下游。
5. 下游无 `.venv` 时可将模板命令适配为裸 `python`；这是启动器适配，不构成
   hook 逻辑 fork。

## 非建议方案

不建议把三个 hook 改成用户级全局运行器：它会使所有项目共享同一套行为，破坏
项目可移植性和版本锁定，并要求 hook 重新设计项目根定位与配置来源。

## 验收建议

- 模板与新建下游项目的三个 hook 内容一致。
- 下游 memory 分类目录能被重复检查与 lint 覆盖。
- 项目设置仅引用项目内相对路径，不包含用户目录或绝对路径。
- 项目对模板的逻辑差异应为零；仅允许解释器路径适配。
