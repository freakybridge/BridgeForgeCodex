## 2. 新收口要求

核心要求：保留受管子包收口，默认复用开发阶段已经取得且仍覆盖最终内容的验证证据，不因进入收口阶段或版本数字变化而重复执行相同测试。升版产生新的实际影响时，仅补齐受影响部分的构建、检查或测试。

1. 保留本次包范围及必要关联影响的判断、版本判级、版本与必要依赖/锁文件更新、版本记录、最终交付一致性核对。
2. 开发阶段的真实验证结果可作为收口依据，前提是能核对其覆盖场景、对应输入、结果及必要环境；聊天中的“通过”不能替代证据。
3. 收口不再默认作为独立的第二轮功能验证。已有证据仍有效时引用它，不为进入新阶段重新执行同样的检查。
4. 升版改变依赖解析、实际构建输入或运行行为时，说明具体影响并补验相关部分。仅版本标识需要编译进产物时，完成必要构建与产物版本核对；是否重跑功能测试取决于实际影响。
5. 证据缺失、失败、中断、输入变化或存在矛盾时，不视为验证已完成；补齐必要缺口，不能借“复用”跳过未完成的验证。
6. 保留无变化不升版、同一内容不重复升版、失败不冒充成功，以及子包开发版本与主程序 release 分工。收口不自动提交、推送或升级主程序 VERSION。

目标路径：开发验证通过 → 确定包范围和版本 → 受管升版 → 核对已有证据是否仍覆盖最终内容 → 仅有新增影响或证据缺口时补验 → 记账并核对交付物。

这是逻辑路径，不要求每个环节新增一次用户确认、文档或工具调用。

## 3. 旧流程与目标的区别

| 项目 | 当前合同 | 新要求 |
|---|---|---|
| 验证安排 | 开发阶段验证后，收口对最终候选执行所选检查，符合现有缓存合同的结果可复用 | 默认复用开发阶段有效证据；仅补新增影响或缺失验证 |
| 升版与记录 | 受管更新版本、依赖/锁和追加记录 | 保留 |
| 最终核对 | 确认版本、代码、记录及声明交付物一致 | 保留 |
| 人工编排 | 无分析预览、分析 JSON、带分析预览、apply、终态核验 | 是否合并入口仍是独立精简候选，本次未决定实现方式 |

假设一个兼容 Bug 修复已通过测试，子包由 2.3.0 升至 2.3.1：若仅版本标识改变且不影响既有验证，复用测试结果；若版本编译进程序，补构建和产物版本核对；若依赖发生实际变化，补相关验证。示例版本不代表仓库实际版本。
