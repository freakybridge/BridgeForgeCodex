# git-sync 历史分析性能

## 范围与授权

2026-10-23 用户要求先测量普通同步与 release，再定位重复历史读取、解析、重建与扫描，实施最小优化并同口径复测。不得跳过发布保护，不修改真实下游、提交推送或部署，不干扰 StratusAgent 正在运行的发布。

用户确认一次性边界：总上限 120 分钟（含前置调研，按本轮约 15:54 至 17:54 北京时间控制）；约 50k token（估算、未实测）；最多 1 个独立审计 Agent；2 轮定向验证。限时交付实际证据与缺口，不自动追加。没有匹配当前会话模型的可靠周额度系数，不虚报周额度百分比。

已授权在 Forge `.runtime/git-sync-perf/` 内保存 StratusAgent 固定历史与工作区隔离副本，仅对副本执行补正、测试升版与本地 Git 同步。唯一测试远端为同目录 local bare；不向 GitHub 写入。固定源 HEAD、文件摘要、工具 hash、环境和命令；样本制作前后有漂移即停止使用该样本。

## 传播与实施顺序

通用产品能力落 `templates/hooks` 并同步 dogfood；测试/基准位于 `scripts/tests`，事实源为本需求文档和本地原始收据。本轮不改 VERSION/CHANGELOG，未来正式 release 处理版本。禁止只改 Skill 或轮询间隔。

1. 可关闭的内存剖析：实际进程计数/耗时、固定提交快照、源码图解析、基线重建、当前扫描、分析校验和序列化。对照工具仅加测量，不先优化。
2. 使用完整真实规模隔离样本，测量 plan/apply、两种 preview、实际 release、普通同步、无变化 release；区分命令启动、CLI、Agent 等待及夹具准备。
3. 仅对实测占比显著的重复工作优化；优先一次调用内复用与批量读，不预设持久缓存。
4. 相同输入、命令和测量口径复测，验证文件/配置/环境漂移、Git 历史解释变化及既有事务保护；复用不受影响证据，不跑无关全量回归。

## 初始证据与限制

Stratus 对话 `01a162d7-8189-7f71-83bb-df92168b6ea8` 的 4.0.1 共享归属计划命令耗时 413.597 秒，apply 耗时 375.036 秒；此前未进入提交推送。其 CPU/Git 观察只能作为线索，不能据此直接认定根因。旧收据没有充分分项计数。

`release_history_cache::Reader` 已有分析内对象缓存，但历史快照与图解析在其上层；重复次数及占比待实测。普通同步路径需单独证明是否进入这些调用。

## 已测瓶颈与最小实现

真实活动工作区快照被前后 hash 检查拒绝（源正处理 fast-forward/stash 冲突），弃用该样本。改用固定 autostash `3077a6d5623250a6ee08ea701c760f2d4ddb78f7` 的 tracked tree 与第三父节点 `998610d188b8609ba1df2327e73e91e53b3e99fa` 的 untracked tree，基于 HEAD `44d7e871d6bc6e22bcda0049884fa640d5159135` 重放。源仓库约 47k 对象、pack 约 386 MiB；副本保留 50 个包、4 个迁移历史节点。共享缺口场景仅将已知补出的 baseline.shared_inputs 置空，其余固定真实输入保留。样本身份见 `.runtime/git-sync-perf/snapshot.json`。

第一组未优化剖析（仅加内存计时器，release 4.0.1 算法不变）：

| 场景 | 命令 wall 秒 | CLI 秒 | cat-file 次数 / 秒 | 源码解析次数 / 秒 | 基线重建 |
|---|---:|---:|---:|---:|---:|
| repair-plan | 312.131 | 311.444 | 1514 / 293.549 | 2415 / 8.553 | 1 |
| repair-apply | 314.616 | 314.553 | 1514 / 296.194 | 2415 / 8.233 | 1 |
| 无分析 preview | 366.62 | 366.473 | 1154 / 223.058 | 1210 / 4.129 | 1 |

无分析 preview 还调用 `show` 221 次（43.207 秒）、`ls-tree` 227 次（45.219 秒）。调用链定位：每个变更路径重建 PayloadClassifier、重新读取 mutable HEAD 合同。另有逐文件 Git 规范化 hash 的开销；其 CRLF/属性语义保留，不以自行散列替换。

由实测选择两项优化：

1. 仅用已登记 baseline.input_hashes 和包 manifest 作为批量预取提示，覆盖固定基线、lineage、HEAD；单 Reader 按 blob OID 去重，重复路径和提交共用不可变内容。失败批次不缓存；提示失败回到原按需检查；partial clone/promisor 状态不作主动预取。当前文件、当前配置、完整指纹和最终历史解释核验仍执行，没有跨进程持久缓存。
2. 输入采集内惰性建立一个 PayloadClassifier，历史读使用已捕获 HEAD SHA。首次合同字节独立保存，后读不一致立即失败，再绑定到 verify_release_inputs；无待分类路径仍不建立分类器。普通 classify 其他调用方不变。

profile 仅在 `BRIDGEFORGE_PROFILE=1` 的 git-sync 命令附加；不改 self-test 合同、不落盘。阶段为 inclusive，不可相加；process 记录启动尝试次数。`wall - cli` 是启动/退出/JSON输出合计残差，不伪称纯启动时间。脚本串行阶段间无 Agent 阅读等待；真实对话等待与原机网络往返不包含在隔离 CLI 数据中。

独立审查曾发现预取失败扩大阻断范围、classifier 保护字节被覆盖及无变化路径提前加载合同三处边界；已修正并补回归，静态复核无剩余阻断。15 项定向安全测试全部通过：首轮 14 项通过，竞争窗口夹具注入点受对象缓存影响未触发预期，修正夹具后仅重跑该项，18.58 秒通过。产品逻辑未因该夹具修正改动。

最终受管 CLI/Hook 已构建成功，源码树 hash `sha256:c9cc1bb9ab6970612f19653f93fc9b786c287967b0fbed85478f94f2c1ad82a0`；新工具 baseline 返回 clean，manifest --check 返回 changed=false。对照 CLI SHA256 `861f82992ac554400dec2cd33cee8934485a4304c4d044d9ee90173bcc9925ed`，候选 `02d94772a43ce1e9a5ff86854ba071b4ca0fb7df3c0300cb16c9aedcdc2dfbf0`。本轮版本仍 4.0.1，未提交推送上游。

基准脚本第一次带分析 preview 因 Windows canonical path 与绝对分析路径不一致而失败（339.223 秒），不是产品优化失败，也不计通过。已改用项目相对分析路径，保留失败原始收据，正式发布段从新宿主重新预览/分析；不复用旧 fingerprint。

## 实测对比

| 场景 | 对照秒 | 候选秒 | 核验 |
|---|---:|---:|---|
| 共享补正 plan | 312.131 | 20.567 | 两侧均 planned |
| 共享补正 apply | 314.616 | 21.208 | 两侧均 repaired |
| 无分析 preview | 358.000 | 51.890 | 146 项差异逐项一致 |
| 带分析 preview | 342.678 | 51.405 | 目标版本、包变更、生命周期事件一致 |
| 有变化 release | 417.457 | 105.538 | 两侧均 synced，仅本地 bare |
| 无变化 release | 51.080 | 50.424 | 不生成新版本，基本持平 |
| 普通同步 clean | 2.286 | 2.153 | 不进入历史图/基线重建 |
| 普通同步 dirty | 34.673 | 33.135 | 保留真实 Hook，基本持平 |

补正 plan/apply 的 cat-file 均从 1514 次降至 6 次；历史快照 10 次、源码解析 2415 次、基线重建 1 次均保留。无分析预览 cat-file 从 1154 次降到 9 次，HEAD show 从 221 次降为 0；固定树读取 227 次降至 6 次。既有逐文件 Git 规范化散列仍是主要剩余开销，不改变 CRLF/属性语义。

第一轮候选未刷新隔离复原后的 Git stat 状态，两个预览通过，但实际 release 的正常状态检查使完整指纹失效，提交/推送前准确阻断。恢复前后内容验证指纹完全一致、146 项差异完全一致，只有完整指纹改变；证据指向复原后的 Git 状态刷新，不声称其为缓存错误。保留失败收据，未替换旧 fingerprint；新宿主从无分析预览重新生成完整分析后成功。基准恢复脚本已在计时前执行普通 status 刷新，与初始对照样本的准备过程一致。尚未用额外冷恢复样本单独验证该解释。

对照 release 中历史快照 5 次、重建 1 次；普通同步 clean/dirty 的历史快照、源码图解析、基线重建均为 0。dirty 对照的 commit_and_hooks 为 23.502 秒，说明其主要开销与历史分析不同。两侧无业务或受管产物重建需求时构建次数均按收据记录为 0，不把开发候选构建计入发布耗时。

文件/配置/环境漂移两侧均以 stale 拒绝，且恢复原文件与环境；没有版本写入、提交或推送。对照耗时分别为 49.036、52.638、48.208 秒，候选分别为 34.994、35.649、35.501 秒；每项 cat-file 均从 142 次降至 78 次，基线重建均为 0（已发布基线场景）。异常路径不降级普通同步。

## 次数、等价性与收口

| 场景 | Git 启动请求：前→后 | cat-file：前→后 | 基线重建：前→后 |
|---|---:|---:|---:|
| repair-plan | 1540→33 | 1514→6 | 1→1 |
| repair-apply | 1544→37 | 1514→6 | 1→1 |
| 无分析 preview | 1840→254 | 1154→9 | 1→1 |
| 带分析 preview | 1844→258 | 1154→9 | 1→1 |
| 有变化 release | 1936→350 | 1154→9 | 1→1 |
| 无变化 release | 238→245 | 73→76 | 0→0 |
| 普通同步 clean | 11→11 | 0→0 | 0→0 |
| 普通同步 dirty | 53→53 | 0→0 | 0→0 |

所有次数来自主 CLI 的 SystemProcessRunner 启动请求；Git/Hook 自身后代进程不重复计数，commit_and_hooks 含它们的时间。源码图解析、当前原生输入扫描、分析文件/指纹校验、规范化序列化 hash、构建与各 Git 操作的微秒/次数均保存在原始 profile；结构化汇总为 `.runtime/git-sync-perf/comparison.json`。未把全部 serde 序列化或版本/锁计算内部子函数逐一计时，不能把规范化 hash 时间声称为全部序列化时间。

无分析预览的主要剩余成本是 Git 的逐输入规范化散列等 other 命令（候选合计 39.294 秒），历史重建已降到 5.673 秒。无变化 release 的历史提示预取增加 3 次 cat-file，总时间基本持平；这是本次最小方案的残留开销，未继续扩张缓存设计。普通 dirty 仍主要消耗于 Hook 和 Git 事务。

两个完整隔离发布结果（包含随后相同普通同步改动）的最终 Git tree 完全一致：`d27e132fa6b9479a8e2cf9bcbb4cd646e4d334c9`。候选 release 收据为 synced、1.54.0→1.54.1、release_plan_reused=true、工作区 clean、ahead/behind=0/0；这些仅属于隔离副本，不是下游正式发布。

成功发布段的三次 CLI 累计端到端耗时（无分析 preview、带分析 preview、实际 release）由 1118.135 秒降至 208.832 秒，约减少 81.3%；补正两阶段另列，不掺入人工等待。单命令 wall 覆盖进程启动至退出，CLI 内部耗时见 profile；启动/退出/输出残差约 0.04–0.69 秒。脚本阶段间 Agent 等待为 0；自然聊天的端到端延迟未测，不能将这些数据当作对话耗时承诺。

原始数据目录：`.runtime/git-sync-perf/results/baseline/`（含首次失败样本）、`baseline-publish/`、`baseline-drift/`、`candidate/`（含首次状态失效）、`candidate-recovery/`、`candidate-drift/`；工具与快照身份、受管构建/基线收据位于同一 git-sync-perf 根目录。可重复测量入口位于 `scripts/tests/benchmarks/git-sync-perf-*.ps1`。

开发交付时 Forge HEAD 为 `7eaad755fc223d896d84ff341f5b568ce675cb10`，VERSION/CHANGELOG 未改，工作区保留本次改动。开发阶段未升级、修改、提交或推送真实下游；未执行 GitHub 写入、全量回归或额外发布准备。后续验收与发布授权见下文。

所有测试远端为本地 bare，不能代替 GitHub 网络耗时或真实下游发布验收。本轮是完整真实规模固定快照的单次配对重放，不是小型夹具速度，也不是统计性 SLA。Agent 等待、权限审核等待、样本准备与开发编译不混入 CLI 耗时；一次自动权限审核超时未启动命令，原样重试成功，独立记录为工具层等待。

## 经验沉淀与用户验收（2026-10-23）

用户明确调用 `$summary accept` 与 `$git-sync release`，验收本次历史分析性能优化，并授权发布本批 Forge 改动。验收复用 15 项定向保护测试、独立审查、受管构建与一致性检查，以及上述完整真实规模隔离对照；不为 summary 重跑构建、回归或审计。

1. 不能从持续 CPU 使用直接推断源码解析是瓶颈。本次实测主要时间来自逐对象 Git 启动，先批量取对象和复用不可变 blob，保留重建/解析次数即可取得主要收益。
2. 主动预取只提供性能提示，不是新的验证条件；失败提示不能扩大阻断，真正需要的对象仍严格校验。缓存只保存当前 Reader 内的不可变对象，不保存跨命令的发布结论。
3. 复用分类器时必须独立保留首次合同字节，不能被后续输入采集覆盖；纯记账/无待分类路径继续惰性跳过。失效后重新生成完整分析，不能换写旧 fingerprint。
4. 隔离恢复、命令启动、CLI、构建、Agent 等待分别统计。固定对象可避免复制活动工作区的不一致；同样的内容验证指纹不代表完整 Git 状态指纹也相同。
