## 现状依据

本轮只读检查了源码、缓存条目和 2026-10-29 的 9.0.0 → 9.1.0 发布收据，历史提交为 `35b5ad7ad1829ceae8805d78abdb759065c6b645`，本机收据为 `.runtime/legacy-seven-upgrade/release-result.json`。该 9.1.0 后续已撤回，见[历史发布与恢复记录](../legacy-seven-upgrade/requirements_2026-10-29_four-projects.md)；这里仅引用其耗时样本，不将它视为当前版本或待恢复目标。

| 观测项 | 历史样本 |
|---|---:|
| 产物准备 | 216.443 秒 |
| 其中 Cargo 构建进程 | 212.263 秒，约占产物准备的 98% |
| 其余准备工作 | 约 4.180 秒 |
| 产物复用 / 重建 | 0 / 3 |

这些是同次调用的嵌套计时，不能相加；构建进程时间包含 Cargo 内部编译、链接等工作。收据未拆分每个产物的构建时间，不能把 212 秒全部归因于某个模块或锁问题。忽略目录收据是本机历史证据，跨机器不可假设存在；后续前后对比应重新取得同场景基线。

已核实的实现：

- [git_sync_plan.rs](../../../source/factory/src/git_sync_plan.rs) 按公共、工厂两种源码投影建立临时构建上下文，最终清理。缓存未命中后，跨次构建无法保留这些上下文中的 Cargo 中间结果。
- [generated_assets.rs](../../../source/core/src/generated_assets.rs) 中 Hook 与 CLI 共用一套 workspace/target，factory 使用另一套，产物按顺序构建；并非三个产物分别完整构建全部依赖。
- 上述两种投影分别调用 [Cache::open](../../../source/core/src/artifact_cache.rs)，但使用同一个项目缓存目录及排他锁。公共缓存成功打开且对象仍存活时，factory 再次申请同一把锁会失败；错误被转为缓存不可用，相关 factory 缓存对象也不能保存构建结果。
- 同进程第二次取锁失败符合现有 [file_lock 测试合同](../../../scripts/tests/unit/core_file_lock.rs)。当前最终产物缓存仅发现 CLI/Hook 条目，与源码判断相符，但本轮未运行复现测试，未测得该问题单独造成的历史耗时。

## 最短执行路径

每个产物依次判断，命中后结束该产物的准备：

1. 已安装产物与本次最终候选一致：按原合同核验并复用。
2. 最终二进制缓存命中：取出并核验，不启动 Cargo。
3. 最终二进制缓存未命中：使用保留的中间结果，由 Cargo 编译必要部分。

不增加固定缓存预热、第二次发布预览、独立准备阶段或固定全量回归。只在原有收据内补两组构建耗时及缓存未命中原因，避免为测量另跑一遍构建。

## P1-1：固定源码副本和 Cargo 产物目录

遵守已确认的[三目录布局方案](../artifact-layout/requirements_2026-10-30_three-directories.md)，新编译缓存进入 `.build/`：

```text
.build/bridgeforge/cargo/
  public/
    source/    公共源码副本
    target/    Hook、CLI 的编译结果
  factory/
    source/    工厂源码副本
    target/    factory 的编译结果
```

- 两套目录跨次复用，不按每次发布指纹重新创建整套目录。源码位置与 target 位置同时稳定，避免只保留 target 却仍不断更换源码路径。
- 只更新内容变化的源码，未变化文件不重写、不刷新修改时间；同步移除候选中已经删除的源码。目录归属和文件集合必须可核验，不能让旧源码或未知文件混入当前候选。
- 版本或少量代码变化不清空整套中间结果，由 Cargo 判断实际重编译范围。工具链、平台、编译配置等不兼容变化时，重建对应组；边界和身份在实现时沿现有环境合同收敛，不另造一套配置体系。
- 中间结果只负责加速，不能替代当前源码、版本、构建配方和最终二进制的核验。保留现有防止误认旧输出的检查，不因持久目录而跳过失败路径。
- 构建结束后保留本方案拥有的源码副本和 target；本次不设计缓存清理器。后续用户执行清理会使下一次恢复冷构建，不能宣称清理后仍保有加速效果。
- 将 `.build/` 纳入项目忽略规则。此项不自动开展完整三目录迁移；与该任务在路径及共享文件上协调，避免反向引入旧目录约定。

## P1-2：按组完成缓存生命周期

将“同时打开多个缓存对象，再统一构建”调整为以下顺序：

```text
公共组：取得锁 → 查缓存 → 必要编译 → 保存缓存 → 释放锁
factory：取得锁 → 查缓存 → 必要编译 → 保存缓存 → 释放锁
两组均成功并通过最终输入核验 → 原发布事务统一安装、提交、推送
```

- 沿用现有缓存和排他锁，不新增独立锁管理系统。每组构建上下文和缓存对象只在该组所需期间存活。
- 固定源码和构建目录在持锁期间使用，锁覆盖源码副本更新、编译和结果捕获；释放前取得待安装字节和收据，不让后续组或进程改变已确定的候选。
- 已安装产物全部可复用的组直接结束，无需打开可写构建目录。
- 锁被其他进程持有时明确报告占用，不能静默当作缓存未命中后并发写入同一构建目录。普通条目未命中与锁失败分别处理。
- 公共和工厂产物仍保持来源与分发边界。两组准备完成前不安装正式产物；输入变化、构建或自检失败沿原事务边界停止，保留用户修改。
- 不重新引入整个 git-sync 的仓库级并行锁；本锁只保护共用缓存与构建工作目录。

## 验证与完成标准

先修组内缓存生命周期，再接入持久构建目录，最后在相同候选、工具链、配置和测量方法下比较前后耗时。使用既有受管测试入口及隔离候选，不依赖真实提交、推送或正式发布才能验证。

| 场景 | 必须证明的结果 |
|---|---|
| 首次构建 | 三个产物对应当前候选，版本、自检和收据一致；取得冷构建基线 |
| 相同候选重复准备 | 已安装或最终缓存复用；通过隔离样本单独证明三个最终缓存条目均可加载，Cargo 构建次数为 0 |
| 仅版本变化、单模块变化 | 未变化源码不被重写，未变化依赖有实际编译复用证据；最终版本正确，记录与原流程同场景耗时 |
| 公共和工厂缓存顺序访问 | 两组均能保存、加载，不发生同进程重入取锁导致的静默降级 |
| 源码删除及环境不兼容变化 | 删除的源码不残留参与编译；不复用不兼容的中间结果 |
| 缓存损坏、其他进程持锁、构建失败或输入变化 | 不误认证旧产物、不同时修改固定目录、不写入半套正式结果；保留原有漂移和回滚保护 |
| 只读 preview/check | 仍不初始化或修改这些缓存目录，不因优化改变零写入合同 |

测试日志、报告和运行数据放 `.runtime/tests/release-build-cache/`，测试编译结果放 `.build/`。已有仍有效的验证直接复用；新增测试只覆盖本方案改变的行为及必要失败路径。

首次缓存建立仍可能较慢，后续提速需要实测，不预先承诺从 216 秒降到某个数值。固定源码目录的残留文件、修改时间、环境变化及并发访问是实施时必须解决的风险，不能为省时削弱输入身份或事务核验。
