# 开发收口与轻量发布

用户已确认计划并要求开始修改、继续。本阶段不提交、不推送、不安装用户级 Skill、不写真实下游。

## 已确认目标

1. develop 完成项目质量检查、独立复核和目标版本产物准备；summary 复用已有证据。后续确认的经验落盘、交接、验收与 TODO 职责见 [Summary 三模式](../summary-workflow/requirements_2026-10-08_summary-workflow.md)。
2. 开发完成且输入未变时，普通 git-sync 同步代码，git-sync release 只增加版本/CHANGELOG/原生 manifest 更新，复用目标版本产物。
3. release 不调用 Cargo、全量回归或 Agent 审计；缺失、损坏、过期记录快速阻断，不在发布阶段补跑长任务。
4. 同步仍保留 fetch、快进、冲突保护、Git index 保护和事务回滚。
5. 耗时验收以用户指令到最终回复为准。CLI 时间只能作辅助，未经真实对话计时不宣称端到端达标。

## 实施范围与预算

- M 级：既有事务中增加准备/消费合同，主对话实施，独立 review-auditor 复核；目标约 45 分钟、20k 新增 token 估算、两轮定向验证。token 未实测；无匹配当前模型的周额度校准，不伪造百分比。若范围或预算不足，保留完成部分并明确剩余动作。
- 产品层通用能力进入 templates/ 与 skills/ 并同步 dogfood；工厂检查配置和清单只在本项目。版本和 CHANGELOG 在后续用户授权 release 时统一生成。
- 复用同一 topic，保留早前 CLI 优化和历史发布记录，不把它们算成本阶段新成果。

## 准备合同

- 受管 CLI 提供只读状态查询与独立准备入口；旧二进制必须先用能力标记判断，禁止试跑未知参数。
- 项目检查清单由 `.codex/development-checks.json` 指定，记录每项实际退出码、日志哈希和耗时；不能用人工一句“测过”代替检查执行。
- 指纹绑定当前仓库、分支、版本、开发输入、检查清单和目标版本；发布事务以原始字节绑定全部非忽略提交内容。
- 交付/缺陷 Markdown 的合法 lifecycle、validation_status 字段不参与开发指纹。后续 Summary 需求增加项目显式 record_documents：仅声明的记录 Markdown 正文允许轻量 UTF-8/结构核验后复用产物；未声明文件、AGENTS、Skill 或配置变化仍失效。发布实例的原始字节检查不会忽略状态字段，防止并发修改漏检。
- 目标版本在隔离快照构建，工作区 VERSION 不提前改写；产物、构建收据与检查结果保存在忽略的 `.runtime`，通过哈希和目标合同核验。
- 工厂独立审计以当前输入指纹的审计记录绑定；记录来源于实际 review-auditor 输出，工具仅验证关联，不宣称能自动完成语义审计。
- 正式发布前后再次核验输入及准备产物；fetch/快进引入新内容时阻断，准备过程不提交、推送当前仓库。

## 验收集合

1. 准备不改工作区业务版本/源文件，不暂存、提交或推送；检查失败、审计缺失/失配不生成 ready 记录。
2. release 消费匹配记录时零 Cargo 调用；目标版本改变、源码/依赖/清单漂移、产物损坏、跨仓库缓存、路径链接均阻断。
3. 合法验收状态变化不失效；未声明正文变化失效，显式声明记录文档经轻量校验可复用；提交说明变化不改变相同目标版本的二进制准备结果。
4. 部分写入、提交拒绝和输入并发变化保持现有回滚与用户文件保留语义。
5. 真实隔离 CLI：准备 → 状态查询 → release → 重复 release；另保留未来真实用户两种调用的端到端验收。

本文件只记合同与验收场景。执行结果以受管准备记录及对话收据为准；准备完成后不再向本文件正文追加验证日志。
