## 3. 目标与行为合同

### R1 跨电脑长期证据

同一有效代码、检查输入及构建/测试条件在 A/B 两端允许复用验证记录。长期证据与严格单次事务指纹分离：前者跨主机复用，后者在当前主机重新生成，不能直接复用另一台机器的发布计划。

源码、检查输入和依赖内容共享确定的身份规则。Git 合同允许的 LF/CRLF 等价表示不导致失效；实际文本、二进制、文件模式及有效规范化规则变化仍应识别。路径以仓库相对身份表示；不得盲目归一化所有文件或忽略路径语义。

长期环境按明确合同记录有效工具身份、目标平台、features/profile、编译选项、相关依赖、SDK 与检查实际依赖的配置。机器名、用户目录、临时目录、工具安装位置、显示和会话元数据不直接导致失效；仍须核对实际解析的工具及有效配置。自定义检查明确登记额外环境依赖，执行环境和证据范围一致；无法可靠界定的检查不宣称跨机可复用。不能只删几个变量或将任意未登记输入静默认定无关。

新记录保存格式版本和可定位的分项身份；develop 写入与 release 比较使用同一实现。差异报告定位文件/字段/检查，不输出环境秘密值，也不未经评估存储低熵秘密的可离线猜测摘要。

### R2 发布需求与检查范围

先保留必要的事务、分类合法性与账本安全检查，再判断本次业务发布需求。纯骨架变化且无有效业务发布目标时返回 nothing-to-release，不受无关历史包证据阻断，不升业务版本。

实际发布以最近正式发布边界以来的累计变化计算范围，包含已提交但未发布的变化、必要包生命周期及累计收口事件；不能只看工作区 diff。检查直接受影响包、真实依赖传播和共享构建/检查合同影响范围。不得因包没有直接文件变化而漏检，也不得全仓包无差别阻断。

release 核验已有开发收口，不自动运行 develop、业务测试、全量回归或自动补升子包。状态入口明确显示证据是否已检查，避免将配置就绪表述为完整门禁通过。普通 git-sync 不以子包收口为前置。

### R3 验证记录与本地产物分离

源码证据有效不等于当前主机产物就绪。本机缺少另一台电脑的构建产物，不单凭此否定已同步的源码验证记录；需要运行/打包时按受管入口生成本地产物。

历史记录只证明当时验证的输入和产物，不自动认证新生成的二进制。合同明确要求的交付产物检查仍保留；用户指定的正式发布若不交付某项本地产物，不将其缺失变成无关阻断。原本作为后续检查输入的产物仍按输入合同处理，不能一律排除。

内容未变、仅重验证据或恢复产物时不重复升子包版本。不增加远程二进制存储/下载服务，不将大文件纳入 Git。

### R4 最小必要发布工作

无业务发布需求尽早退出，避免先生成各业务包内容、环境、依赖、产物摘要再决定无须发布。有发布需求时先限定影响范围再读取/计算证据，公共输入单次采集复用，不先全仓计算再过滤。

预览、分析和执行之间复用仍有效的结果；fetch/快进或实际输入变化时按影响使缓存失效，最终写入前仍核验输入漂移。缓存不可仅凭 mtime 或旧收据无条件放行。必要构建仅在发布确需且无有效产物时执行；不取消项目规定的轻量提交、版本及 Git 保护。

性能目标是不做无关扫描、重复摘要或隐式测试；总耗时必须用同条件前后数据说明，不预先编造秒数/SLA 或速度提升比例。

### R5 历史兼容

旧账本和链保持原样。可证明等价的记录受控复用，无法证明时指出所需受管重验证范围，不改旧摘要冒充通过。不将开发证据格式升级与 release schema 4 混淆；未知格式明确阻断并说明升级条件。

## 8. 本轮经验沉淀（普通 summary）

1. **先定义可复用的有效条件，再计算长期证据。** A/B 的源码和工具条件可以等价，机器名、安装目录、会话信息却不同。长期记录采用显式环境合同，单次计划继续防漂移；未知旧摘要不能靠改字段重新认证。仅更新骨架不会自动使未接入合同的旧检查变成可移植检查。
2. **缩小发布范围时，必须盘点提前返回之后的保护。** 空包范围可以省去无关包指纹，但发布仍会写版本和变更日志，Git Rules、显式全局输入、缺失状态及目录成员的 guard 仍须传到最终消费者。此次两类遗漏均先取得反例，再验证零写入拒绝及恢复后正常执行。
3. **develop 与 release 必须共用影响语义。** release 要求验证的旧包，develop 必须能选择并补验；“尚无记录”不等于“新增代码”。以已验证 baseline 和真实归属变化判定 level=0，保留新增包、源码变化和实际依赖要求变化的升版路径。
4. **范围判定与历史证据算法分别演进。** 锁注释及迁移新增空字段不应制造业务影响。范围选择可使用 TOML 语义和已验证的初始配置，但不能顺手替换 schema3/4 摘要算法、重写旧链或把未知历史当作等价。
5. **性能结论必须覆盖成功路径，并保留不利样本。** 无业务退出、缺记录阻断、实际 release-planned 是不同场景。此次保留单包分批变慢样本，再以旧/新 CLI 交替配对核对；不把预览指标扩展成真实 fetch/Hook/推送耗时。
6. **候选生成前固定输入，完整失败后仍按失败交付。** 审计补改与构建交错造成清单反复过期；完整检查又暴露范围不一致和测试夹具问题。静态审查、定向绿测及早期 prepared 均不能覆盖后续失败。受管恢复/回滚保留原账本和源码，最终收口必须针对当前输入重新取得证据。
