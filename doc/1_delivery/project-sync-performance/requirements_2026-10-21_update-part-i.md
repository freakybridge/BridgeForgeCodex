## 目标与范围

以官方目标提交判断本机产品源能否复用：同提交且本机有效时不 clone；需要获取版本时只准备经验证的临时产品源，交给后续用户级 CLI 准备环节。

随后由 update part II 完成用户级组件的统一安装与验证，消除事务后重复 doctor；普通 update 不再检查 Native Memory 同步状态，仅在明确需要迁移 Hook 注册时处理该注册。

update part III 专注项目级差异、定制、一次性兼容迁移提示和计划输出；用户级工具及公共产物准备作为前置条件，不将公共 CLI、公共 Hook 的版本、缓存、构建或安装匹配判断重新纳入本阶段。项目自有 Hook 的源码、依赖、构建、运行和正常注册维护归项目开发流程；普通 update 不承担这些职责。

update part IV 复用项目计划，将待安装内容补齐并完成必要校验，作为安装前的内部准备步骤，不新增独立命令调用，不编译任何 Hook，也不提前修改项目正式文件。

update part V 执行项目事务：一次执行前复核与原文件快照、一轮安装结果验证、一次轻量终态核对；保留必要授权、项目锁、文件漂移保护和准确的失败回滚结果，删除同次操作的重复规划、判断与验证。

公共产物准备到项目安装的跨段归属已按 U-1 确定：part II 准备、part V 安装，项目继续保留匹配自身骨架版本的副本；迁移记录、缓存目录、内部接口和检查证据结构等工程合同需在实现前明确。离线升级不在本次范围，不将未实现的方案描述为当前运行行为。

## 完整 update 流程概览

| 顺序 | 阶段 | 输入与输出 | 写入边界 |
|---|---|---|---|
| 1 | part I：上游探测与本机产品源准备 | 查询官方目标提交；复用有效本机源或取得经验证的临时源，绑定本轮提交。 | 不提前替换正式产品源。 |
| 2 | part II：完成用户级更新事务 | 准备并验证可共享的公共 CLI/Hook，统一提交产品源、用户级 CLI、Skills、用户 AGENTS 等配套组件；向后交付确定的公共产物。 | 不写下游项目；CLI 验证归事务、不重复 doctor，普通 update 不巡检 Memory。 |
| 3 | part III：生成项目更新计划 | 比较项目级受管内容和定制，轻量判断明确迁移，输出动作、风险、阻断和指纹。 | 只读，不编译、不写项目或缓存；有风险汇总决定，有阻断停止依赖动作。 |
| 4 | part IV：准备项目所需产物 | 复用计划和内容，仅补齐待安装字节与必要校验，内部交给 part V。 | 不单独调用命令，不编译或安装，不执行项目 Hook。 |
| 5 | part V：执行项目更新 | 同一项目事务安装 part IV 的项目内容和 part II 已确定的公共产物，执行前复核与快照、验证、最后写戳并返回结果。 | 仅安装、不重新构建公共产物；失败按实际情况回滚，外部改动不得被回滚覆盖。 |

公共 CLI/公共 Hook 复用同一有效构建产物，各项目分别安装自己的版本副本；公共程序与配置共同安装、共同回滚。上游未变化只免去 clone，不能直接推定项目无需更新。项目内容计划无变化不代表固定公共产物没有安装动作，完整 no-op 必须同时考虑二者；迁移提示的状态记录按 E-4 完成设计，不能因骨架内容无变化丢失已授权的待迁移状态记录。

## 已核实事实

- 用户级产品源为 `~/.bridgeforge-codex/`，用户级 CLI 为 `~/.codex/bin/bridgeforge.exe`；两者不是同一路径。
- 当前 updater 正常路径先创建临时官方 clone，再展开工作树、验证来源与 manifest，之后判断本机组件是否需要更新；尚无先比较官方提交并直接复用产品源的快捷路径。
- 当前来源验证包含官方 origin、分支与提交、工作树、路径和资产验证；现有 `Assert-Repository` 仅接受系统临时目录内的源，新增本机复用路径需要显式适配验证职责，不能直接放宽所有源入口。
- 产品 home、CLI、Skills、用户 AGENTS 与 ledger 属于共同事务；不能先提交新版产品 home，再尝试准备 CLI。
- 当前 Skill 在 updater 完成后单独调用 doctor，再运行 memory-sync status；这是待修改的现状，不是本卡确认后的目标行为。
- 用户级 Native Memory Hook 注册在 `~/.codex/hooks.json`，调用 `~/.codex/bin/bridgeforge.exe memory-sync hook-run`；日常事件同步不依赖某个项目的 CLI。更新 CLI 与迁移 Hook 注册是不同动作，不能因为更新程序就默认需要改注册。
- 当前 `project_sync::build_plan_with_inputs` 会读取项目身份与目标合同、计算受管内容变化、风险和项目 Hook 输入；CLI 的 project-sync 入口还会调用 `attach_generated_assets` 后才返回预览。当前预览可能构建产物，不能把本卡目标中的只读项目计划描述为已经实现。
- 当前单文件项目 Hook 借用受管 workspace，其构建身份包含公共 workspace 和锁文件哈希；独立 Cargo 工程模式已有自己的文件身份，但构建、入口包装和收据检查仍有骨架参与。`project_hooks.rs`、`project_hooks/package.rs` 与 baseline 调用链需一起调整，不能只跳过编译而保留导致常规 update 失败的旧绑定检查。
- 事实依据为 `scripts/bridgeforge_codex_shared_update.ps1` 的 `Assert-Repository`、`Get-RepositoryIdentity`、`New-CommandHomePlan` 和 `Invoke-Main`，以及 `skills/bridgeforge-codex/references/user-skill-maintenance.md`。

## update part I：已确认规则

以下编号固定为本次确认的 1–7 项，不代表每个分支都按七次操作执行。

| 编号 | 规则 |
|---|---|
| 1 | 每次更新先查询官方 GitHub 目标分支的提交号；沿用现有官方来源与目标分支，不另设发布通道。 |
| 2 | 上游提交与本机一致，且本机产品源完整、未被修改时，直接复用，不 clone。 |
| 3 | 上游提交变化或首次安装时，获取到临时目录并验证；沿用受管获取与验证方式。 |
| 4 | GitHub 查询失败时停止，不自动使用旧版本继续升级；离线升级不纳入本次范围。 |
| 5 | 本机产品源存在未知修改、来源异常或不安全路径时停止，不自动覆盖。 |
| 6 | 本次操作绑定一个确定提交，源码、模板与合同必须来自同一版本；上游在查询后变化时，不能混用查询与获取的不同版本。 |
| 7 | 临时产品源准备成功后，交给后续 CLI 准备环节；全部组件就绪后再统一事务提交，不提前替换正式产品源目录。 |

## update part I：输入、输出与失败语义

| 对象 | 含义 |
|---|---|
| 输入 | 现有官方仓库与目标分支配置、本机产品源及其实际完整性和来源状态。 |
| 成功输出 | 本轮选定的提交身份，以及经验证可供后续 CLI 准备读取的现有或临时产品源。这里描述语义，不预定新增接口字段。 |

## update part II：完成用户级更新事务

### 已确认规则

| 编号 | 规则 |
|---|---|
| II-1 | 产品源、用户级 CLI、受管 Skills、用户 AGENTS 与安装 ledger 作为配套组件统一准备、验证和事务提交；未变化的组件不重复替换。这里的提交仅指本机安装生效，不是 Git 提交或推送。 |
| II-2 | CLI 验证合并到用户级更新事务，由事务证明安装程序与目标产品匹配、来源及文件完整、自检有效；同次操作复用仍有效的准备阶段证据，安装后核对实际目标。 |
| II-3 | 用户级更新成功后，普通 update 不再额外重复运行完整 doctor。doctor 作为独立诊断工具保留；不能把取消重复命令理解为取消必要校验，也不能用失效证据继续项目更新。 |
| II-4 | 普通 update 不调用 Native Memory 同步状态检查，不将健康、pending、busy、同步失败或冲突巡检作为普通项目骨架更新的固定步骤。日常同步和重试仍由已有 Hook 与 worker 负责。 |
| II-5 | 只有目标版本明确需要迁移 Native Memory Hook 注册时，update 才处理对应注册。迁移不等于健康巡检、首次启用或完整 Memory 同步；保留既有授权与禁用状态，不借迁移扩大远端、目录或可见性。首次启用、主动诊断及修复属于独立流程。 |
| II-6 | 任一组件准备或安装验证失败，不得报告用户级更新成功；保留现有回滚与中断恢复语义。part II 成功只证明用户级工具已就绪，不代表下游项目已升级或 Memory 真实事件运行已通过验证。 |
| II-7 | 按 U-1 统一准备并验证目标公共 CLI 和公共 Hook；匹配的共享产物直接复用，供多个项目安装。向 part V 交付绑定本轮目标的固定产物描述及有效证据，不提前写项目目录，不把公共 Hook 安装为用户级项目事件 Hook。 |

### 输入、输出与自动化边界

- 输入：part I 绑定的产品源与提交、匹配目标产品的 CLI 候选或有效已安装产物、其余用户级组件的更新计划及有效授权。
- 输出：配套且验证通过的用户级安装结果，供 part III 生成项目计划使用；另有前置确定的公共产物及证据供 part V 安装。结果字段的具体设计留待实施，不在本卡虚构接口。
- 当前卡不规定 CLI 构建缓存的新位置、身份合同或首次构建方式，只规定验证与提交的职责归属。
- Hook 注册迁移必须由明确版本变更和可识别旧注册驱动；未知注册或授权边界变化不能静默覆盖。迁移与用户级组件的失败一致性必须在实施中验证，不能引入“工具已更新、必需注册迁移失败却报告成功”的状态。
- 不在此阶段修改下游项目；不执行 Memory reconcile，不读写记忆正文来代替注册迁移验证，不变更用户级 Memory 长期授权。

## update part III：生成项目更新计划

### 已确认规则

| 编号 | 项目级工作 | 边界 |
|---|---|---|
| III-1 | 识别项目现状 | 读取项目骨架版本、配置和已有资产，识别非法版本身份、降级等阻断问题。 |
| III-2 | 比较项目骨架内容 | 按目标合同列出项目内受管文件的新增、更新、合并或退役动作；相同内容不产生更新动作。公共 CLI、公共 Hook 的产物判断不包含在这一项。 |
| III-3 | 处理项目定制 | 保留项目自有内容，识别合并冲突与迁移事项；需要用户决定时展示具体对象和影响，不自动覆盖未知内容。 |
| III-4 | 轻量判断一次性兼容迁移 | 只按明确迁移声明、适用旧版本与已记录迁移状态判断是否需要提示；首次涉及的旧项目有限核对注册和必要工程文件。常规 update 不全量分析项目 Hook 源码/依赖、不检查其开发构建是否最新、不生成常规重编任务。细则见下方已确认解耦与迁移规则。 |

### 输入、输出与自动化边界

- 前提：part I / II 提供有效的目标产品源和用户级工具；公共产物准备归前置职责，不由 part III 重新决策。公共 CLI 可作为执行规划的工具，但不是本阶段的检查或更新对象。
- 输入：目标项目、绑定的目标骨架合同、项目版本与相关文件、明确迁移声明和迁移状态，以及已有有效迁移或保留决定。项目 Hook 注册仅按保留与迁移需要读取；不将其完整源码、依赖树和构建产物纳入常规规划输入。
- 输出：项目级动作和风险分类、阻断项、相关输入与计划的指纹。具体字段沿现有合同实施适配，不在本卡预设不存在的接口。
- 计划无项目修改时报告本阶段无需处理；只有自动更新项时交后续流程；需要用户决定时汇总确认；有阻断时停止依赖动作。项目计划无变化不能替代前置阶段或全流程的最终收据。
- 指纹用于后续判断计划依据是否变化；确认后发生相关文件或输入漂移，不能照旧计划静默安装。执行前复核与原文件快照按 part V 合并处理，必要的现场安全检查不能以复用为由跳过。
- 计划成功不表示项目 Hook 构建成功、更新成功或用户验收通过。用户业务代码、业务依赖升级、业务回归不因生成骨架计划自动纳入范围。
- 公共产物按已确认 U-1 由 part II 准备、part V 安装；part III 不重做版本、缓存、构建或安装匹配判断。执行前仍须统一核验固定安装项的目标路径、ownership、授权范围和实际文件状态，不能以“机械复制”为由覆盖未知同名文件。

## 已确认补充：项目 Hook 解耦与一次性兼容迁移

本节替代此前“普通 update 检查项目 Hook 构建身份并按需准备”的方案，不新增日常巡检链。

| 编号 | 规则 |
|---|---|
| D-1 | 项目 Hook 自己拥有源码、Cargo 工程与锁文件、入口、依赖、构建、自检及运行方式；不依赖骨架私有源码、受管 workspace 或骨架 update 生成业务运行入口。仅新增 Cargo.toml 不足以宣称完成解耦。 |
| D-2 | 项目开发导致的 Hook 新增、代码或依赖变化由项目开发流程处理。普通骨架 update 不编译、修复或替项目维护这些开发产物，也不自动补做业务验收。 |
| D-3 | 项目拥有自己的 Hook 注册，骨架更新共享配置时保留项目注册、参数和已有程序，不因为公共模板变化覆盖、退役或重新生成它们。旧注册格式的必要迁移只能按明确声明处理。 |
| D-4 | 产品以稳定迁移身份声明一次“项目 Hook 解耦”兼容迁移，注明适用旧版本范围与处理说明。具体首次发布版本和机器字段在实施时确定，不虚构版本号，也不借此抬高既有 compatibility_baseline。 |
| D-5 | 常规 update 只读取轻量版本与迁移状态：不适用或已完成时直接跳过；首次涉及的旧项目仅有限核对注册和必要工程文件。完整依赖分析、适配、构建及行为验证只在用户明确启动迁移后执行。 |
| D-6 | 区分未提示、已提示待迁移、迁移完成和不适用等语义；已经提示不能记成完成。已提示且声明未变化时不重复展开诊断或弹出同一提示，主动查看维护状态仍可见待迁移事项。具体状态字段与持久化位置留待实施合同确定。 |
| D-7 | 仅发现旧耦合时提示并允许继续；只有目标升级确实会破坏旧 Hook 的已有运行或注册合同，才阻断相关更新并说明具体依据，不把所有未迁移项目一律阻断。不能将整套工作区哈希变化本身当作实际不兼容证据。 |
| D-8 | 一次性迁移与普通 update 分开，迁移前需要明确项目范围和授权；迁移保留原行为、输入输出、退出码、超时和 Windows 隐藏启动语义。完成后依据实际验证记录完成状态，不能以“用户看过提示”或“骨架版本已更新”替代。 |
| D-9 | 同步解除旧构建身份与 baseline 的连带绑定，使普通 update 不再因公共源码变化而要求项目 Hook 重编；保留必要的项目自有区保护、明确不兼容阻断和安装事务校验，不把删除所有检查当作解耦。 |

### 迁移状态与只读规划的衔接

- part III 只读规划仍须零写入；不能为了标记“已提示”就在计划阶段写项目或缓存。提示展示与状态保存的具体事务位置须在后续实现合同中明确，只有获得相应维护写入授权后才记录；纯预览不承诺跨调用持久去重。
- 待迁移状态必须能跨普通骨架升版保留，不能在本次升版后因项目版本离开旧版本区间就被遗忘；完成状态由迁移证据决定。
- 同一迁移身份和有效状态只触发一次有限识别；声明或相关注册发生可观察变化时仅针对变化做重新判断，不以“防止过期”为由每次扫描完整 Hook 源码和依赖。
- 确需阻断的不兼容条件必须每次有效：已提示或已读状态不能屏蔽阻断，也不能作为兼容证明。迁移结果无法核实则不能宣称完成。
- 本阶段不读取或分析下游私有业务正文来做全量审计；不使用 Native Memory 同步状态承担项目 Hook 迁移状态。

## update part IV：准备项目所需产物

去掉项目 Hook 编译后，本段定位为“把项目计划变成可安装内容”，不是常规构建阶段。以下方案已获用户确认，作为安装前的内部准备步骤执行，不单独调用命令。

| 编号 | 已确认工作 | 与其他阶段的边界 |
|---|---|---|
| IV-1 | 接收有效计划及必要决定 | 复用 part III 的计划和既有授权；有未决风险或阻断时不提前安装，也不另跑一套完整规划。 |
| IV-2 | 准备待安装文件内容 | 复用已经计算的模板、配置及保留项目定制后的合并内容；只补齐计划确实需要且尚未物化的字节，不重复渲染全部文件。删除动作只携带精确清单，此时不删除。 |
| IV-3 | 做准备阶段的必要校验 | 核对本轮待安装内容的完整性、格式、目标路径与计划一致性；已有有效证据复用。源或决定漂移则停止，不把准备阶段变成全项目健康巡检或完整 baseline 重跑。 |
| IV-4 | 交付给安装事务 | 携带待写内容、精确删除清单、保留决定、输入身份和验证结果给 part V；可使用内存或必要的隔离临时区，不强制新建持久“安装包”或额外通信文件。原文件回滚快照与最终锁内复核由 part V 负责。 |

- 无新增内容需要准备时应为轻量直通，不为阶段名称而强制编译、复制全目录或生成包。
- 不构建公共 CLI、公共 Hook 或项目自有 Hook，不自动迁移项目 Hook，不处理 Native Memory 同步，不执行业务测试或业务 Hook 行为。
- 不修改项目正式安装、不写版本戳；准备失败时项目保持原状。真正写入、回滚和终态验证属于 part V。
- part IV 只作为内部准备步骤，不新增独立 CLI 命令、单独进程往返或额外用户确认。内部函数如何组织属于实现细节。

## update part V：执行项目更新

### 已确认事务步骤

| 编号 | 工作 | 边界 |
|---|---|---|
| V-1 | 核对必要决定并取得项目更新锁 | 对有效计划的授权、未决风险及阻断状态集中判断；拒绝条件不得先产生项目写入，不重复询问已有决定。 |
| V-2 | 复核相关文件并保存原内容 | 写入前核验计划及输入仍有效，同一份可靠读取同时用于漂移检查与回滚快照，避免分别读取两遍。 |
| V-3 | 执行精确写入和删除 | 同一事务安装 part IV 的项目内容与 part II 前置确定并验证的公共 CLI/Hook；固定公共产物项也纳入精确写入、快照、安装验证及回滚范围，不重新选版本或构建。保留项目自有内容与 Hook，禁止计划外清理、全目录覆盖或覆盖未知同名资产。 |
| V-4 | 验证安装结果 | 完整验证本次受管安装的文件、配置结构、保留内容和删除结果符合目标；不重新执行项目 Hook 的源码/依赖/开发构建健康检查。 |
| V-5 | 最后写版本戳并核对终态 | 安装验证成功才写骨架版本戳；随后复核相关已验证内容未变化及戳与目标一致，复用有效规则检查结果，不重新完整遍历执行同一套语义检查。 |
| V-6 | 返回本次实际结果 | 返回版本、实际修改、剩余事项及回滚状态；完整成功收据用于收口，不自动提交/推送或追加无异常依据的同类检查。 |

失败进入回滚分支：恢复本事务能够证明归属的写入；目标已被其他程序改变时保留外部状态并准确报告回滚未完成，不能强行覆盖或声称全部恢复。现有代码的错误回滚不能当作已证明支持进程崩溃/断电恢复；若后续需要增强该能力，必须单独明确合同与验证范围。

### 已确认检查精简

| 编号 | 重复点 | 处理规则 |
|---|---|---|
| V-R1 | Skill 在 Apply 前额外重规划，而 Apply 入口也规划 | 取消 Skill 那次重复完整规划，由执行入口集中完成必要复核。跨命令确需恢复内存计划时只保留必要的一次，不把重复编排包装成安全检查。 |
| V-R2 | Apply 内对不变计划两次判断相同风险授权、gap 和 blocker | 合并为一次入口判断；实际文件漂移和授权范围变化仍须处理。已确认允许继续的迁移提示不能沿用旧的“任何 gap 都阻断”语义。 |
| V-R3 | 漂移检查和回滚快照分别读目标文件 | 合并读取与校验，保留路径安全、目标状态及写入前必要一致性检查。 |
| V-R4 | 版本戳前后两次完整基线验证相同资产 | 完整安装验证一次；终态以内容未漂移和版本戳断言复用有效证据，不只看版本号、mtime 或仅凭项目锁假定内容没变。无法证明证据有效时不得省略所需复验。 |
| V-R5 | 基线反复核对项目 Hook 源码与构建收据 | 按解耦规则取消常规绑定，保留项目自有注册与内容保护；明确兼容迁移仍按 D 规则处理。 |
| V-R6 | 事务成功后由 Agent 再跑同类检查 | 有完整且无异常的收据就收口；只在证据缺失、失效或出现新异常时针对性补验。 |

写入前的计划有效性、写入后的安装正确性和版本戳终态属于不同断言，不能当成同一重复检查删掉。项目锁只能协调遵守它的更新进程，不阻止编辑器或其他程序写入；实施时必须以故障注入证明证据复用与外部改动保护不退化。

### 工程合同的拟定方向

1. 公共产物缓存由当前用户拥有，位于产品源码树之外，采用不可变构建身份和明确 ownership。身份覆盖源码、锁文件、配方、自检、目标平台及可建模环境；未知环境关闭复用或明确报错，不能猜测相同。缓存容量有界，只清理能证明归属且未使用的项目。
2. updater 保留必要的受管 Rust 引导，不新增脚本替代业务实现。初次构建的 CLI 与公共 Hook 共享依赖构建目录；不同目标程序可分别执行正式 Cargo 配方，不把“只构建一次”误解成全程只能执行一条 Cargo 命令。
3. part II 产物描述包含不可变身份、内容校验和来源证据；part V 持有有效引用后安装，不依赖更新期间可能被另一进程替换的产品 home 内容。III/IV 不再生成公共产物的选择或构建决策，但所有固定写入项必须进入项目执行授权、ownership、漂移和回滚保护。
4. 预览和 Apply 不强制持久化整份计划作为进程间通信。沿用可验证输入与指纹传递，跨进程需要重新形成内存计划时只做必要的一次；进入安装事务后复用同一内容与原文件快照。
5. 迁移状态拟区分本机提示去重与项目完成证据，状态写入归获得授权的维护动作，纯预览零写。处理无文件安装动作但有通知状态变化、更新失败重试、后续版本继续提示/阻断等路径；不触碰原生 Memory 内容或状态来承担该机制。
6. 在隔离环境中用无法访问产品源、两个项目不同版本和同名注册等场景验证 B-1–B-3；不通过重命名真实用户目录或实际执行下游业务 Hook 来制造测试条件。

## 验证范围与验收轮次（实施预算内）

| 编号 | 验证层 | 范围与关键断言 |
|---|---|---|
| T-1 | 上游探测与产品源 | 同提交 clone=0；仅非构建内容变化不会因提交号本身重编，产品版本变化按正式身份处理；来源异常/网络失败/变化竞态停止；临时准备失败不替换正式安装。 |
| T-2 | 公共构建与复用 | 一个全新隔离用户先冷构建，再相同输入重复维护及更新第二个项目，公共产物不重复编译；真实构建与模拟计数分别记录。覆盖缓存损坏、身份失效、并发、中断、旧 CLI 引导和自检失败。 |
| T-3 | 项目 Hook 解耦与迁移 | 常规 update 不编译、不全量扫描项目 Hook；旧耦合首次有限提示，重复不巡检，待迁移跨升版保留；真实不兼容仍阻断。迁移只对隔离样例显式执行并验证原行为，不修改真实业务项目。 |
| T-4 | 项目计划与准备 | part III 零写入、零构建；part IV 不独立命令、不重渲染全部文件。覆盖定制保留、风险、旧 Rule/Memory 资产决定与漂移；这里的 legacy 项目资产迁移不等于 Native Memory 同步。 |
| T-5 | 项目事务与去重 | 文件读取复用不丢漂移检测；公共程序与配置共同回滚；戳前/后篡改、外部编辑、未知产物、安装失败不误报成功。验证调用次数，同时核验实际结果，不能只为减少次数删断言。 |
| T-6 | 三项架构边界 | 隔离项目 A/B 各自运行项目 CLI，公共 Hook 注册与执行根不串项目；项目自有注册保留；隔离产品源不可用时日常项目命令/Hook 及用户级 Memory 入口不回读该源。Memory 外部行为用隔离远端或测试替身，不使用真实记忆。 |
| T-7 | 兼容与工厂传播 | 模板/dogfood 源码逐字一致、Skill metadata、manifest、project structure、baseline；共享模块变动还覆盖 git-sync、release、Memory 命令及注册的相关回归。必要时运行已有 init/adopt 夹具证明共享变更不回归，但不扩大为全新工作流重设计。 |
| T-8 | 完整工程与性能 | 按 `.codex/development-checks.json` 完成全部检查、完整 workspace 与 factory fixtures，并按开发收口要求取得审计和准备收据。旧/新实现使用同场景、同环境对照，记录源探测、构建次数、复用、规划、检查与总时间；不把内部 CLI 时间等同于真实用户端到端等待。 |

性能样本至少包括冷启动、同项目重复 update、同版本第二个项目 update、仅项目文件变化、旧 Hook 迁移提示重访五类；能重复的对照交替运行三组并报告中位数与波动。冷启动首次引导、公共 CLI 和公共 Hook 各自编译次数单列，父子阶段计时不相加。不会预先承诺固定提速百分比。

每轮验收由必要定向/故障注入、相关回归、完整工厂检查、审计及性能证据组成。预算包括首次完整验收及一次实质修复后的完整重测；无新改动/失败/未解风险时不反复跑完整集。权限重试和输出恢复不单计轮次，但计入时间/token；同一问题连续两次实质修复失败按项目规则停止并升级研判。

未纳入默认工程验收：真实用户级安装、真实 GitHub 发布/推送、真实下游 worktree 写入或业务 Hook 副作用、真实 Native Memory 同步。若后续授权真实测试 worktree，另明确范围并记录现场证据；没有这类证据就标为未验证，不把隔离 fixture 冒充真实下游/runtime 通过。

## 规模、预算与停止点

- 首次需求落盘采用 S 级记录任务预算：20 分钟、8000 新增 token 估算上限、0 个子 Agent、一次文档核验及最多一次修复重测。该口径只覆盖首次记录，不代表后续整个讨论或实施预算，也不重置此前消耗。本轮用户要求复核完整需求，按项目 AGENTS 增加 1 名 review-auditor 执行有限只读复核及最终差异复核；token 未实测，不把独立复核写成 0 Agent 或声称累计预算已经实测通过。
- 整体实施为 L 级架构与迁移任务。已获授权的执行上限：12 小时、100000 新增 token（估算，未实测）、最多 1 名独立 review-auditor、最多 2 轮完整验收。主 Agent 负责实施，审计 Agent 只读复核并可在第二轮复用，不另启动实现 worker；预算按本次实施累计。
- token 预算包括主 Agent、独立审计、调查、代码/测试/文档、合理返工、验证与收尾；此前需求讨论不声称已经实测计入，不能据此伪报整段对话总消耗。预算按后续执行累计，阶段/Skill 切换不重置，编译等待和权限重试计入时间。
- 时间分配：合同/基线 1 小时、part I/II 与公共复用 3 小时、解耦及 part III/IV 2 小时、part V 1.5 小时、传播/完整检查/审计/性能 2.5 小时、环境重试及修复余量 2 小时，总上限 12 小时。分项用于容量规划，不作为各阶段重新审批或自动追加预算的理由；预判完整验收放不下时提前停。
- token 分配参考：合同/基线 12000，part I/II 28000，解耦及 III/IV 20000，part V 14000，传播/验证/审计 16000，返工余量 10000，合计 100000。子 Agent 成本包含其中，不再重复加算。
- 历史依据：2026-10-20 构建复用交付记录曾出现完整 workspace 约 38.8 分钟、预计完整检查与隔离构建 60–75 分钟，并经历磁盘、长路径、PowerShell 环境故障和多次返工；本次影响面更大，因此预算含完整验收与环境余量，不能按 S/M 默认时间承诺。
- 周额度粗估：用户本轮明确授权沿用旧临时系数 0.152 个百分点/10000 token，来源为本机 `.runtime/task-budget/weekly-quota.json` 中此前 gpt-6-astra standard、text-code、`input_tokens-cached_input_tokens+output_tokens` 的 provisional 记录。原样本含并发干扰，本轮模型/速度未核实；该系数仅作为用户选定的粗估，不升级为校准事实。计算 `100000 / 10000 * 0.152 = 1.52`，展示约 1.5%。预计消耗约 100000 token，占周额度约 1.5%。
- 达到任一执行上限或预计余量不足以完成必要验证时停止新增工作，保存真实状态与剩余项；不得自动扩额、删减验收、改为真实下游试错或创建其他任务绕过。若需要新进程崩溃恢复体系、任意项目业务迁移或无法建模的公共构建环境，先停相关动作并重新界定范围。
- 若需要扩大为离线升级、改变来源/分支、自动覆盖未知本地内容、先替换正式目录或修改后续 CLI/缓存合同，停止相关动作并回到对应需求确认。

| D-01 | 新项目 Hook 或已解耦项目 | 项目有独立依赖、入口、构建/运行/注册维护方式，不依赖骨架源码与普通 update 生成产物。 |
| D-02 | 无迁移适用性或已完成迁移 | 不触发项目 Hook 源码/依赖扫描、构建、自检及业务行为；普通路径仅有轻量版本/状态判断。 |

| D-04 | 同一声明已提示、仍待迁移，随后普通升版 | 不重复展开诊断或弹出相同提示，待迁移事项不因骨架升版消失，已提示不等于完成。 |
| D-05 | 仅发现耦合或目标确实破坏运行合同 | 前者提示并继续，后者阻断相关更新并给依据；通知去重不得屏蔽实际阻断。 |

| D-07 | 用户明确启动迁移并完成验证 | 保持业务行为、输出、退出码、超时和隐藏启动语义；只有具备实际迁移证据才记录完成。失败或未授权不得修改为完成。 |
| IV-01 | 项目计划及必要决定有效 | 内部复用原计划，不新增独立准备命令或额外确认，不完整重做规划。 |
| IV-02 | 目标文件内容已在规划阶段计算 | 直接复用有效内容，只补齐实际缺少部分；无工作时轻量直通，不强制复制全目录或打包。 |
| IV-03 | 准备内容、路径或输入发生漂移 | 停止准备并交回对应处理，不提前写正式文件、删除目标或写版本戳。 |
| IV-04 | 普通项目安装准备 | 不编译公共/项目 Hook 或 CLI，不迁移项目 Hook、不处理 Memory 同步、不执行业务测试；交付内容与计划精确对应。 |
| V-01 | 已有有效计划和全部必要决定 | 不再由 Skill 额外完整规划；Apply 对相同授权/阻断状态只作一次入口判断，仍核验实际输入。 |
| V-02 | 项目内容在规划后或准备过程中变化 | 写入前识别并停止；同一份原文件读取用于漂移核验与快照，不把过期快照当回滚依据。 |
| V-03 | 安装成功 | 仅执行精确计划动作，安装完整验证一次，版本戳最后写，终态核对实际内容和戳；不自动执行额外重复检查。 |
| V-04 | 完整验证后、版本戳前后发生外部修改 | 不把先前语义验证直接当作当前状态；终态不能误报成功，回滚不得覆盖外部改动。 |
| V-05 | 安装或校验失败 | 能完整回滚时准确报告；无法恢复的路径保留现场并报告回滚未完成，不误报成功或全回滚。 |
| V-06 | 旧项目 Hook 只产生兼容迁移提示 | 不因任意 gap 一律阻断；只有明确实际不兼容阻断相关更新，不重建项目 Hook 或伪造收据。 |
| V-07 | 用户级事务成功，项目规划阻断或安装失败 | 单独报告两段结果，不撤销已完成的共享用户级安装；项目回滚不影响其他项目或用户级 Memory 使用的程序。 |
