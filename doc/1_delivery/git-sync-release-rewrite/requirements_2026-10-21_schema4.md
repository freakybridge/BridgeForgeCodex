## 3. 已确认的 14 项业务规则

| 编号 | 规则 |
|---|---|
| R-01 | B 包升级，不自动使依赖它的 A 包升版。A 自身文件、公开接口（含转发的 B 接口）或依赖要求发生变化，才单独判断 A；必要重编不等于升版。 |
| R-02 | 包所属发布文件的任何变化均触发该包升版，包括代码、注释、格式、文档、增删和重命名；仅适用下述明确例外。 |
| R-03 | 公共 Cargo.lock 是程序级发布输入，不直接触发业务包升版。 |
| R-04 | 任意位置的 Cargo.lock 都遵守此例外；仍保留并严格校验，支持构建、依赖解析和产物追溯。 |
| R-05 | 有发布相关变化的正式发布提升程序 VERSION，包括仅测试变化；普通提交不自动升版。 |
| R-06 | 按每个包自身变化定级：修复、重构、注释、文档等为 patch，兼容功能为 minor，不兼容接口、数据或使用要求为 major。程序建议取本次实际变化的最高级别，不能将一个 feat 提交涉及的全部包都定为 minor。 |
| R-07 | 支持用户指定版本；未指定包名的目标属于程序，指定包名仅针对该包，支持多个独立目标。 |
| R-08 | 指定版本低于自动建议直接拒绝，不再次询问、不擅自替换目标；不得覆盖或复用已发布旧版本。 |
| R-09 | 比较上次正式发布与当前最终状态。中间修改后完全恢复的包不升版，不能仅累计提交触及路径。 |
| R-10 | 实际依赖变化可以引发策略新构建，不自动提升策略包版本。构建编号、收据和自动构建记录不触发包升版；实际参与业务的生成源码和资源不属于此例外。 |
| R-11 | 本次引入且尚未接受的不兼容变更阻断发布，直至修复或用户明确接受影响及迁移范围；有效授权不重复询问，major 版本号本身不代表接受。 |
| R-12 | 按实际影响范围验证，复用仍有效证据；新增失败和关联不明的失败阻断，有证据证明无关的历史失败记录但不阻断。 |
| R-13 | 支持无业务内容变化的显式纯升版，记录原因，仅处理指定对象，程序仍按整体发布规则处理。无发布相关变化、无显式版本目标的普通发布保持 no-op。 |
| R-14 | 仅全局工具链或编译参数变化，且包自身文件、公开合同及依赖要求未变时，只改变构建身份，不自动升包；正式发布时程序升版。包自身 Cargo.toml、build.rs 或源码变化仍按 R-02 处理。 |

不得声称只靠任意代码差异即可可靠推断语义兼容性。Agent 给出逐包说明并不替代事实与证据；Rust 核验实际差异覆盖、包归属、版本约束、证据适用性和漂移。兼容性不确定或未接受的不兼容按 R-11/R-12 停止，不默认降低级别或伪造通过。

## 4. schema 4 与历史交接边界

1. schema 4 是唯一新建和执行发布的合同，不保留 schema 1、2、3 旧算法作为 fallback。
2. 日常发布使用最后正式发布的新格式基线和当前最终状态；迁移时可读取更早历史，带入必要的包身份、已发布版本及退役约束。
3. 保留 Git 历史，不重写已发布记录；不得把当前 HEAD 直接设为新起点，以跳过尚未发布的改动。无法可靠还原时明确阻断。
4. 工厂以一个产品发布，内部原生 manifest 版本作为产品映射。下游可以登记多个独立包；两种结构共用 schema 4 核心。
5. 旧项目正式 release 前需要完成迁移；普通不升版 Git 同步不因策略退役额外强制业务验收或全量测试，原有 Git、配置安全及产物有效性检查保留。
6. 首版承接现有 Rust/Python 能力；不新增其他语言的独立包适配器，不把 Stratus 业务规则硬编码进公共实现。
7. Agent 在发布时产生逐包级别、理由及用户明确目标，Rust 执行确定性核验和事务。无新增风险时复用既有有效发布授权，不新增逐包重复授权流程。
8. 项目发布检查显式配置。业务验证在发布前由项目完成，发布入口只核对适用性及必要检查；不把工厂 development-checks/prepared 收据强加为所有项目的发布前置。
