# 开发交接、经验沉淀和轻量发布的经验

本记录来自 2026-10-08 当前对话及源码、测试和独立复核证据。现行职责见[需求卡](requirements_2026-10-08_summary-workflow.md)；本文保留原因与经验，不另建流程事实源。

| 问题与弯路 | 已确认原因 | 处理与适用边界 |
|---|---|---|
| summary 只展示聊天总结，没有形成可复用文档 | 旧 Skill 明确禁止普通模式写任何项目文件，限制与用户希望沉淀开发经验的目的相反 | 普通 summary 就应写 doc；验收是额外授权，不能把“写经验”误当“验收关闭”。重复调用只补新信息 |
| 用 CLI 耗时说明 git-sync 速度，用户看到的总耗时却长得多 | 工具内计时没有包含调查、重复检查、审计、等待和最终回复 | 体验指标使用用户输入到最终回复；CLI 时间仅作分项。没有真实端到端测量不得承诺达标 |
| 发布时又编译、全量检查，增加等待 | 开发收口与 Git 发布混在同一流程；后移检查没有减少总工作 | 开发完成质量检查和目标产物准备，release 复用有效记录；开发耗时仍须完整披露 |
| 验收写文档和 TODO 后，刚准备好的发布又失效 | 最初准备指纹把记录正文与代码输入一并绑定 | 项目显式声明记录类 Markdown，单独做轻量 UTF-8/结构检查；配置清单、Skill、AGENTS、代码及未声明输入仍严格绑定。记录变化若实际提出代码调整，必须重新开发与验证 |
| 合法状态字段在开发指纹中可忽略，但发布并发修改也可能被忽略 | 原发布绑定复用了规范化哈希，独立复核指出 active/in_progress 改为 completed/in_progress 会漏过内容比较 | 发布实例改用原始字节清单，结构检查前后和写入前后都核对；开发证据复用与本次提交内容一致性是两种不同要求 |
| 自动状态快照很多，但最近完整工作交接仍停在旧日期 | Hook 只保存 Git 等客观信息，无法推导需求、决策、完成程度和下一步 | 退役会话自动/手动快照；summary switch 写可随仓库同步的交接，另行 git-sync。交接文档不等于未提交代码备份或本机缓存 |
| 删除 Skill 后，旧引用仍留在测试和其他流程 | 分发、路由、行为 fixture 和操作文档各自引用名称 | 退役要检查真实调用和显式登记；隔离安装验证原版移除、定制漂移拒绝，不能只证明源码文件消失 |

## 已有证据与未验证范围

- 对话和源码确认了旧 summary 的零写入限制、Hook 的 Stop/PostCompact 自动快照和手动入口。
- 定向测试覆盖记录文档复用、源码/Skill/配置保护、非法文档及并发内容绑定；完整检查和审计最终结果记录在需求卡及本机准备收据，不在此重复维护计数。
- 本机源码修改不等于用户级 Skill 已安装；真实下游、另一台机器接续和真实发布端到端耗时，必须在各自实际执行后再确认。
- 开发收口后实际补写交付验证记录，再次调用 release-status 仍返回 prepared、record_documents_changed=true、record_documents_check=passed，开发指纹未变。这证明允许范围内的记录落盘可与产物复用兼容；不能推广成任意 Markdown 改动都无需重新验证。

## 复用方法

先区分需要保存的内容：经验写主题文档，工作接续写交接，待办写总表，验收状态写已有交付记录。用相对路径互相引用。少量客观状态可以辅助核对，不能替代完整任务说明或作为新授权。
