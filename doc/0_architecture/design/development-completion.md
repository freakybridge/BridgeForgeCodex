# BridgeForge 工厂开发收口

本合同只约束工厂自身。通用 develop 读取本合同，不将工厂检查下沉到项目模板。

子包开发收口与主程序发布遵循[版本生命周期设计](package-version-lifecycle.md)。使用实际 CLI 能力与收据核验，不手工升版或伪造完成；旧工具缺能力时分别报告开发验证与版本收口状态。既有工厂检查和性能边界继续保留，独立发布候选准备已退役。

## 1. 开发完成的判定

需求已实现、按影响范围选定的必要验证通过、适用审计完成且剩余限制说明清楚后，完成实际受影响子包的受管版本收口再交付；没有子包变化不新增此步骤。能力未实现时单列“开发验证已完成 / 子包版本收口未完成”。开发不要求主程序发布预览、主程序目标版本分析、隔离发布候选构建；子包版本分析归开发收口，不与主程序发布准备混同。

遵循 develop 共用 D1–D5：明确任务 → 调查与实现 → 验证与修正 → 适用收口 → 交付。工厂传播四问并入首次影响判断；本合同只补工厂检查和产物边界，不另起第二套开发流程。无关历史问题单列，不要求全仓清零。先稳定源码、确定候选版本，把必要检查安排到最终候选；相邻验证/记账可一次受管 apply 完成，不先在外部重复相同检查。需要分开时使用版本合同的 validate/apply，并引用有效任务证据；缺完整环境声明不猜造复用资格。实际版本/依赖/构建影响才补验，不因文档或收口措辞改变重复冷构建。

## 2. 按影响范围选择验证

| 层级 | 适用改动 | 必要验证 | 扩大条件 |
|---|---|---|---|
| A：文档与规则 | AGENTS、Skill 文案、设计与记录文档；不改可执行逻辑或构建输入 | 实际 diff 与规则一致性；相关编码、链接、结构检查；受管资产变化时核对 manifest / dogfood | 规则改变执行入口、权限或发布行为时补流程场景审查；不因文件名是 AGENTS/Skill 自动跑 Rust 全量 |
| B：局部实现 | 单一功能、Hook、校验器或工具行为 | 受影响单元/回归，相关调用方与失败路径；影响 CLI/Hook 时补针对性集成或 smoke；需要产物时验证最终受管构建 | 发现跨模块影响或定向覆盖不足，明确补测对象和依据，再扩大 |
| C：广泛或高风险 | 公共接口、迁移、事务、发布归属、依赖/工具链等广泛影响 | 定向验证稳定后，运行一次能覆盖风险的相关集成集；风险跨越全局时才选择完整 workspace、完整 fixture | 记录为何定向验证不足、具体完整检查与成本；不将所有公共区或规则变更机械归为本层 |

选择以实际行为与依赖为准，不只按文件数或目录名。开始验证前，用短清单明确“改动 → 风险 → 检查 → 可复用证据”，写在原需求记录或交付输出中；不新增验证框架、必填 JSON 或独立审批卡。用户限制验证范围时遵从本轮授权，并如实列明未覆盖项。

检查完成后立即收口；不把已明确排除的下游、网络或自然生命周期验证替换成更多离线测试。独立审计按根 AGENTS 的触发条件及实际风险选择；普通文案自查不强制增加子 Agent。

## 3. 工具、构建与性能检查

- baseline、skill metadata、manifest `--check`、project structure、mirror drift 各自覆盖不同风险，按变更选择；无需把它们及两个完整测试集每次全部运行。Skills 未变不重跑其专项检查，Rust 未变不重跑 Cargo 镜像测试；已有适用证据可复用。
- 需要完整 Rust 验证时，先核对模板与 dogfood 一致，再在 dogfood 跑选定测试；同一测试不在两个镜像重复执行。完整命令见根 AGENTS 快速命令，定向命令使用真实 package / test filter，确认执行数量，不能将筛选到 0 项视为通过。
- 工厂测试从根 `Cargo.toml` 的九包 workspace 执行；`.codex/hooks/` 是不含工厂测试源码的八包公共投影，只验证其锁定构建与公共入口，不对它启用 `bridgeforge_factory_tests`。本次检查从版本合同的 development 登记中选择。
- 当前版本产物与发布候选产物分开判断。构建只在实际构建输入变化、现有产物缺失/不匹配或需要验证构建链时执行；使用受管构建和真实收据，不伪造 hash 或更换未受管入口。Windows 刷新目标程序时避免运行中的目标镜像占用；环境失败先定位原因，不循环冷构建试错。
- 性能任务先建立同方法基线，优先测受影响场景；定位并修正问题后再扩大测量。分别记录被测命令与夹具准备/清理耗时。后者过重时先评估夹具复用，不仅靠增加样本和时间。修复后按实际影响复测；复用其他候选数据时说明分支依据、候选身份与统计限制。
- 长检查开始前核对已有实际耗时与剩余工作。新失败先分析影响再决定重测；不得以固定档位不断追加测试、构建或时长代替排查和范围选择。

## 4. 证据复用与交付

1. 记录检查命令或收据、覆盖场景、真实结果与对应输入；有现成指纹时复用，不为小任务搭建额外指纹系统。
2. 相关源码、依赖、配置、产物及必要运行环境没有变化时，复用已通过结果。局部修复只重验受影响部分；说明未变部分为何仍适用，不因无关文档变化否定所有结果。
3. 仅修改说明、索引或验证记录时，复核相关文本、链接与结构即可。AGENTS/Skill 若改变执行语义，仍需审查相应流程，不用“文档变化”掩盖行为风险。
4. 失败、超时、中断和未执行均不算通过；静态审查、夹具、真实下游及自然 runtime 证据分开报告。必要证据缺失时限定交付结论，不补造验证或验收状态。
5. 交付实际改动、所选验证与复用依据、子包收口和已知风险；用户验收、Git 保存和正式发布分别记录。开发收口不提交、推送或升级根 VERSION；子包版本按通用受管合同处理。

## 5. Git 与发布边界

- 普通 git-sync 不依赖子包收口；release 须核验受影响包已完成验证与升版，缺口即停止，不补跑 develop。新收口门槛不等于要求旧开发 JSON、全量回归或用户验收收据。保留 baseline、编码、版本、构建身份及 Git/暂存树保护。
- 普通同步不主动升版；子包在 develop 收口升版，主程序版本及正式 CHANGELOG 由获明确授权的 release 事务处理。release 不再次升子包，完整公告累计包版本变化；必要构建复用有效缓存，不组织业务全量测试或用户验收。
- 同步期间 fetch/快进或实际输入、环境变化使发布分析失效时，按现有受管流程重新生成；不得仅替换旧 fingerprint。提交 Hook 若改变已核验暂存内容，保留现场并阻断推送，不自动 reset。
- summary 记录实际证据，不因总结自动补跑完整测试、启动发布准备或更改长期规则。
