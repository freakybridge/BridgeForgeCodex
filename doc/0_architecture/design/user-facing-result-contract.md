# 用户可见结果语言合同

## 目标

BridgeForge 的机器接口继续使用稳定英文枚举，面向用户的结果统一使用简体中文。
用户不需要理解内部状态模型，也能直接判断本次操作是否结束、是否需要确认以及下一步做什么。

## 三层边界

| 层次 | 内容 | 兼容要求 |
|---|---|---|
| 用户结果 | 固定中文结论、待处理事项、下一步 | 禁止直接倾倒内部枚举、traceback 或资产清单 |
| 技术收据 | 稳定代码前缀、路径、字段和值 | 只在诊断或用户追问时展示 |
| 机器接口 | JSON 字段、英文枚举、退出码 | 禁止因文案统一而改名、翻译或删除 |

## 固定用户结论

| 内部状态 | 用户结论 |
|---|---|
| `ready`、`completed` | `已完成。` |
| `unchanged` | `无需处理。` |
| `planned`、`confirmation_required` | `等待确认。` |
| `blocked`、`failed` | `未完成。` |
| `completed_with_gaps`、`degraded` | `已完成，但仍有待处理项。` |
| `advisory` | `提醒`，不算失败 |

结论可以通过“待处理事项”补充当前对象和原因，但不得另造近义状态词。

## 输出格式

面向用户的操作结果必须按固定顺序提供：

1. `结论`：只使用上表中的固定结论。
2. `待处理事项`：没有待办时明确写“无”。
3. `下一步`：给出一个可执行动作；已经结束时明确写“无需继续处理”。

Hook 和诊断脚本可以保留 `[component] BLOCKED`、`ADVISORY` 等稳定技术前缀，
但同一行必须给出中文用户标签和中文动作。技术前缀不充当用户结论。

### 编码自检例外

`config_health_check.py` 和 `encoding_check.py` 负责发现 UTF-8 环境或文本编码已经损坏的场景。
在 UTF-8 输出能力尚未被证明时，它们允许使用纯 ASCII 英文诊断，避免中文错误信息本身变成乱码。
该例外只适用于编码自检的失败收据，不得扩展到普通同步器或业务 Hook。

## 验证红线

- 用户文案调整不得改变机器 JSON、退出码、事务、回滚或确认语义。
- 同一状态的 Template、dogfood 与主程序输出必须一致。
- 新增用户结果时必须加入固定结论测试；禁止只靠文档约定。
- 技术术语首次面向用户出现时必须给出中文含义；技术收据中的字段名保持原样。
