# 用户可见结果语言合同

## 目标

BridgeForge 的机器接口继续使用稳定英文枚举，面向用户的结果统一使用简体中文。
用户不需要理解内部状态模型，也能直接判断本次操作是否结束、是否需要确认以及下一步做什么。

## 三层边界

| 层次 | 内容 | 兼容要求 |
|---|---|---|
| 用户结果 | 固定中文结论、待处理事项、下一步 | 禁止直接倾倒内部枚举、traceback 或资产清单 |
| 技术收据 | 稳定代码前缀、路径、字段和值 | 只在诊断或用户追问时展示 |
| 机器接口 | JSON 字段、英文枚举、退出码 | 禁止因文案统一而改名、翻译或删除 |

同步器错误必须先经过稳定分类，再进入用户结果。已分类错误使用确定的中文原因和下一步；
未分类错误只能显示通用中文停止说明，禁止拼接原始异常。原始异常继续保留在 `machine`
技术收据中，供诊断和当前版本调用方使用。

## 固定用户结论

| 内部状态 | 用户结论 |
|---|---|
| `applied` 且 `execution_status=succeeded` | `已完成。` |
| `current` 且无 gap/blocker | `无需处理。` |
| `planned` 且 `confirmation_required=false` | `可直接执行。` |
| `planned` 且 `confirmation_required=true` | `等待确认。` |
| `blocked`、`failed` | `未完成。` |
| plan 有 gap 或未完成决定 | `等待确认。` |
| 项目成功但独立用户级检查有待处理项 | 主对话并列报告用户级事项，禁止把它伪装成项目收据字段 |
| `advisory` | `提醒`，不算失败 |

测试收据缺少明确退出码时保留 `exit_code=null`、`source=unknown`；进程仍运行、已返回 session_id 或仅无报错，都不能作为测试通过证据。

收据只识别直接测试程序及其支持的调用形式，不搜索普通参数、注释或字符串中的命令名。PowerShell 的引号表达式与 Bash 的引号程序名分别处理；只有单一、可静态归属的命令才接受结构化退出码。多命令、管道、重定向、动态参数及中断的结果保留未知，不从输出正文中的“exit code”推断成功。

结论可以通过“待处理事项”补充当前对象和原因，但不得另造近义状态词。`可直接执行。` 只表示计划已经具备执行条件，不表示更新已经完成。

## 输出格式

面向用户的操作结果必须按固定顺序提供：

1. `结论`：只使用上表中的固定结论。
2. `待处理事项`：没有待办时明确写“无”。
3. `下一步`：给出一个可执行动作；已经结束时明确写“无需继续处理”。

Hook 和诊断脚本可以保留 `[component] BLOCKED`、`ADVISORY` 等稳定技术前缀，
但同一行必须给出中文用户标签和中文动作。技术前缀不充当用户结论。

### 编码自检例外

Rust Hook 的 `config-health` 和 `encoding` 检查负责发现配置或文本编码已经损坏的场景。
在 UTF-8 输出能力尚未被证明时，它们允许使用纯 ASCII 英文诊断，避免中文错误信息本身变成乱码。
该例外只适用于编码自检的失败收据，不得扩展到普通同步器或业务 Hook。

### 发布版本公告

release 成功时，主对话必须完整展示主程序及自上次正式发布以来所有版本变化的子包：名称或稳定 id、旧版本、新版本、变化原因。该清单是用户结果，不是可省略的技术收据，也不受代码效果摘要三条上限限制；未变包可只汇总数量，新增/退役分别说明。失败时区分计划与实际状态，不把计划版本称为已发布。

子包版本由 develop 收口生成，release 只读取累计结果并升级主程序；未收口时报告具体包及补齐动作。以实际 CLI 能力与 `package_changes` / `package_events` 收据为准，状态与规则见[版本生命周期设计](package-version-lifecycle.md)，不得以本文代替运行时证据。

## 验证红线

- 用户文案调整不得改变机器 JSON、退出码、事务、回滚或确认语义。
- 同一状态的 Template、dogfood 与主程序输出必须一致。
- 新增用户结果时必须加入固定结论测试；禁止只靠文档约定。
- 技术术语首次面向用户出现时必须给出中文含义；技术收据中的字段名保持原样。
