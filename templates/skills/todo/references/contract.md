# TODO 管理与收口合同

> todo、confirm 落盘、summary accept 和 TODO 查询时读取。本文件拥有操作规则；字段、状态和归属的机器事实源是当前项目 `.codex/hooks/source/checks/src/todo_contract.json`，也可用 `.codex/bin/bridgeforge.exe check todo --root . --contract` 只读输出。非 Windows 去掉 `.exe`。入口缺失时读取实际合同文件，不猜测接口或运行安装。

## 记录与身份

- 固定路径、六列、七个状态、两种归属以机器合同为准。确有获准事项才创建“项目待办总表”，登记 doc/README.md，不创建空占位表。
- 新增由 todo 或获准落盘的 confirm 完成；已有记录的状态、内容、归属与链接维护由 summary accept 完成；查询只读；不支持删除。
- 新编号为历史最大数字加一，从 TODO-001 起且至少三位；不复用、不重排。按 ID 或同一事项先去重，唯一匹配只引用原编号；有歧义时询问，不覆盖旧记录。
- 一条记录对应一个可独立完成的事项。原需求记录事项最初目标，正式确认后关联需求卡；待确认的新想法可以暂无需求卡。后续事项保留来源，以稳定 TODO ID 在总表独立承接，不能把原需求未完成验收改称后续事项。
- 关联文档使用带角色的链接：`[需求：名称](相对路径)`、`[来源：名称](相对路径)`、`[验收：名称](相对路径#验收段)`、`[取消：名称](相对路径#取消决定)`。路径相对总表且位于项目内，来源/证据可核验。待确认事项暂无正式文档时注明本轮用户输入，不制造链接或需求包。
- 总表只存摘要、进展和来源；正式需求、验收和取消决定保留在关联文档。旧格式需要显式适配授权，不自动改写其他项目历史。

## 状态与收口

- 未确认为待确认；已确认未开始为待执行；已开始为进行中；处理结束缺验证为待验证；验证完成缺用户验收为待验收。按实际证据选择阶段。
- 已完成必须满足本事项条件并取得用户验收，保留验收链接；机器检查要求验收链接指向已收口且验证通过、明确提及本 TODO 编号的正式记录，正文仍须核对实际用户决定。原交付已验收不能代替后续事项的完成证据。
- 已取消须明确用户决定和原因，保留取消链接，不当作完成。误标或证据冲突由 summary accept 更正并说明依据，不抹去历史决定。
- 正式决定记录写明本 TODO 的完整编号和实际用户决定。优先补充已有来源文档；无来源且本次明确获准记录取消/验收决定时，summary accept 按 doc/README.md 布局在当前 topic 新建最小 `decision_YYYY-MM-DD_TODO-NNN.md` 并登记索引，保存编号、用户决定、日期、原因和必要证据。不补造需求或开发验收；取消记录不将原任务标成已完成。缺授权或证据时保留原状态并报告，不能只改总表。
- summary accept 仅更新本次授权范围内相关条目；明确发现的新独立问题按 todo 新增规则记录。普通 summary、switch、开发、查询和 Hook 不自动维护 TODO。

## 归档与只读检查

- 正式需求卡/Bug 收口记录决定原交付状态；过程报告的旧状态不能单独推翻验收。原需求范围内未关闭的关联 TODO 阻止归档；独立后续事项继续由总表承接，不阻止已验收原交付归档。
- 归档仍须用户确认移动；归档方案包含活动引用和 TODO 链接迁移。TODO 关联链接由 summary accept 按明确授权维护，未获对应授权不移动；路径迁移不改变状态、归属或编号。
- 获准写入后运行 `check todo --root .`，归档和工程结构检查共用此规则。损坏表格、重复/乱序编号、非法状态/归属、缺失/越界链接或缺收口证据时报告，停止依赖该结果的动作；检查零写入，不安装或自动修复。
- 缺机器入口时核对实际文件并说明未执行机器检查。检查不能替代验收正文与用户决定复核。
