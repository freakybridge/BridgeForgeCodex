# develop — 按规模交付开发任务

## 定位与边界

消费已有需求、授权和预算，组织实现、验证与交付。
需求确认及规模、预算口径由 confirm 管理，不重复访谈或复制其阈值。
纯咨询和只读方案保持只读；本流程不授权提交、推送、发布或其他项目写入。

子包版本由开发收口负责，主程序版本由 release 负责；涉及项目自有子包时读取[子包收口与项目特殊流程](references/completion-release.md)，核验实际 CLI 的开发与稳定判定能力。能力缺失时单列未完成的版本收口，不得手工改号、伪造收据或调用旧 release 代替。

## 1. 选择执行路径

1. 复用仍匹配当前任务的规模、需求、授权和预算。
   缺少规模或预算时读取 confirm 的“规模与预算硬闸”；
   缺少记录时整理已有决定，只补问会实质改变结果的未决项。
   新报或调整预算使用 confirm 的周额度预估口径。
2. 根据规模选择路径：

| 规模 | 执行方式 | reference 读取条件 |
|---|---|---|
| S | 主对话直接实现、针对性验证、简短交付；不补需求卡、不启动子 Agent | 涉及注册子包或项目要求收口时，仍读 completion-release |
| M | 使用有效需求卡，默认由主对话调研与实现 | 读取 M/L 交付；确需 Agent 时再读 Agent 执行 |
| L | 使用有效需求卡和完整预算，按依赖关系分段执行 | 读取 M/L 交付和 Agent 执行 |

[M/L 交付](references/ml-delivery.md)
[Agent 执行](references/agent-execution.md)

3. 原 S 级任务因明确要求而需要需求卡或独立审计时，按 M 级核算；
   复用已有授权和预算，仅预计超额时补问。
4. 项目声明结构化开发记录、发布准备或特殊收口流程时，
   再读取[项目特殊收口](references/completion-release.md)。
   项目强制检查始终有效，不因 S 级而省略。
5. 有效实施授权直接进入执行；需求确认不代表实施授权。

## 2. 实现与验证

1. 修改前核对直接调用点、受影响行为和失败路径，
   复用已有有效调查，不为凑齐流程重复扫描。
2. 以“用户动作 → 预期结果 → 所需检查”选择最小验证集，
   纳入项目强制检查和受影响的既有功能。
   小任务简短说明即可，不为验证另建卡片或审批阶段。
3. 仅改变字体、颜色、文案，且不影响布局测量、交互、
   业务逻辑或告警含义时，采用轻量验证：
   核对直接调用点与相邻样式，完成必要构建及针对性检查；
   默认不新增测试框架、不运行无关回归、不启动独立审计。
   轻量验证不免除项目要求的受管开发收口，也不授权删减配置中的必需检查。
   涉及共享布局、文字测量或语义变化时，按实际风险补充检查。
4. 优先使用已有检查。需要新增测试时，应覆盖本次风险或回归，
   不为简单常量修改创建只复述实现的测试。
   全量测试或额外审计须有项目要求或具体风险依据，并在预算内。
5. 与运行环境有关的问题按用户实际入口验证，
   核对相关启动方式、构建模式、编码、配置和产物。
   使用替代环境时，明确其覆盖范围及未验证的差异；
   不把工具环境通过扩大为用户环境通过。
6. 交付可试用程序前，按项目入口完成必要构建，
   核验目标产物与本轮修改的关联。
   项目专属命令和产物检查由项目流程维护；
   构建及产物核验通过不代表功能或桌面效果通过。
7. 复用仍有效的调查、测试和收据：
   相关源码、依赖、配置、产物或验证环境变化，
   或出现矛盾证据时，仅重新检查受影响部分。
   不为无关文件变化否定全部结果，也不为复用临时搭建指纹系统；
   项目已有正式指纹或收据机制时遵守该机制。
8. 结果在原需求记录或既有收据中补充，不重复创建同类记录。
   S 级用实际输出说明结果，不为流程补文档。
9. 约定验证和项目必需检查取得充分证据后，按受管合同完成受影响子包的版本收口；同一批已收口内容不重复升版，主程序 `VERSION` 不变。无子包变化不增加收口步骤。
   按 [收口流程与完成状态](references/completion-release.md) 核验终态；预览出现额外包时先查明归属与原因，不直接全包升版，也不据此跳过收口后宣称完成。
   需收口而未执行、执行失败或中断时，开发仍未完成，明确阻断及继续条件；
   缺少桌面或真实环境验证时如实标注，不以更多离线检查代替。

## 3. 范围、预算与停止

- 普通实现细节自行处理；范围、行为、接口、验收或风险
  实质变化时，仅重核受影响的授权。
- 扩大范围、启动子 Agent、运行全量测试或进入再次实质修复前，
  按 confirm 核对剩余预算；预计超额时暂停超额动作。
- autopilot 继承同一任务包、整体预算和停止条件，
  不重新套用子任务默认预算，不重置累计或创建替代 Goal。
- 缺授权、关键输入或必要验证受阻时，仅暂停相关动作，
  说明原因、已有成果和恢复条件。
- 修复失败计数与升级遵守公共 AGENTS；恢复后从卡点继续。
- 必需独立验证不可用时，可以报告已有成果，
  但不得宣称该项验证或整项验收完成。

## 4. 交付

- 先说明开发整体状态，再区分代码修改、工程验证和受管收口。需收口但未取得有效结果时，明确写“开发未完成”，列出阻断包、原因、继续条件及 release 影响；不能仅写“构建通过、未升版”。终态依据见 completion-release，不把命令退出码 0、执行过 preview 或版本文件已变当作收口成功。
- 实际改动及用户可见行为。
- 实际验证命令、结果和覆盖范围；复用证据说明其仍有效的依据。
- 未通过、未验证项和试用主路径。
- 子包版本收口结果、旧新版本及原因；自动进入 `1.0.0` 的依据或保持 `0.x` 的缺口。未具备受管能力时如实报告，不将开发验证通过等同于版本收口完成。
- M/L 附唯一需求卡、验证状态及预算使用情况；
  S 级简短说明按规模闸免需求卡，预算沿用已有口径。
- 需要独立审计时附真实结论；未要求时不为收据启动审计。
- 实现完成、工程验证、用户验收和 Git 发布分别报告，
  不相互替代，不自动 git add、commit 或 push。
