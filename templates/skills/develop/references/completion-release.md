# 子包收口与项目特殊流程

> 涉及项目自有子包，或项目声明结构化开发记录、发布准备及特殊收口流程时读取。
> 核验 `package-development-v1` / `package-stability-v1`、`task-selected-development-checks-v1` 与 `version-coverage-v1`；按任务范围还需 `task-scoped-development-v1`。开发验证与受管版本收口分别报告。

## 本次范围与完成条件

明确本次涉及的注册包 id，使用 `develop --packages <id1,id2>`，并在预览与 apply 中保持相同选择。工具自动纳入注册依赖、调用方及相关身份变迁；以 `effective_task_packages` 核对展开范围，不能删掉真实必要包。版本记录覆盖整包，不支持只登记同包中的若干修改行。

无 `--packages` 的入口保留全仓诊断；不能用全仓清零替代本次完成判断。只有测试策略或宿主环境变化不会重新打开已有版本记录；源码、依赖或实际构建输入改变仍须处理。工具缺少所需能力时报告缺口，不编造参数或退回全仓强制升版。

## 1. 子包版本收口

版本判级、两个基线、自动进入 1.0.0 的条件及证据边界统一见[版本生命周期合同](../../git-sync/references/schema4.md)，不另维护第二套规则。

1. 修改前核对项目注册包、版本来源和工作区已有变化；需要判断既有收口状态时执行零写入 `develop --preview --packages <id1,id2>`，留存实际输出。没有修改前证据时标为归属待核实，不能把额外包默认归为历史问题。无变化不升版，同一内容重复运行不重复升版。
2. 在已授权的开发范围完成适用验证与必要审计，复用仍有效证据；不把工厂全量检查套到其他项目。
3. 按版本合同预览并生成分析，为每个实际待处理包在 `validation` 中选择非空的已登记检查，说明如何覆盖本次风险；Cargo test 可在原参数末尾、原 `--` 之前追加一个测试名过滤条件，不替换原命令、目标或参数。保留所选检查的输入、产物和执行边界，以及项目明确必需的检查；自动 1.0.0 仍执行完整 core/integration 稳定检查。核对带分析预览后 apply，工具对最终候选实际执行检查，不升级主程序 VERSION。可选缓存遵守版本合同，不以聊天记录代替执行。
4. 核验版本、相关依赖/锁、收口记录及最终交付产物一致；写版本造成实际产物或验证影响时补齐对应检查。失败不留下已认证的半成品。
5. 最终产物稳定后，以相同 `--packages` 核对版本覆盖和声明交付物；相关包仍待处理时定位具体缺口。版本覆盖有效不等于当前机器已验证运行，环境变化不自动引发整包重验。报告版本变化、实际检查、稳定缺口和范围，主程序发布和用户验收分别记录。

当前工具缺少新能力时，明确报告“开发未完成：开发验证已完成 / 子包版本收口未完成”，说明升级工具等继续条件，保留证据并停止版本写入；不得调用旧 release、手改 manifest 或伪造新收据补齐。确认本次不涉及注册子包及其验证输入时，可说明收口不适用及依据，不额外制造记录；项目既有发布阻断仍须单列。

### 预览出现额外包

`affected_packages` 是待分析、待验证范围，不是批量升版清单。结合本次 diff、修改前状态、包登记、依赖关系、版本记录和声明交付物逐包区分：

- 本次直接修改及必要连带影响：完成适用检查和受管收口。版本/交付覆盖有缺口而内容未变时由受管计划决定是否无升版刷新；只有环境或检查策略变化不重开版本，不统一强制升版。
- 可证明的既有未收口变化：保留其来源和现场；复用已有授权，否则只询问处理该独立范围所缺的决定，不替它编造兼容性或通过证据。
- 疑似工具或环境误判：先定位输入和可重复证据。包数量多本身不证明误判；未查明时列为未决阻断，不自动忽略、升级工具、修改检查配置或修复其他项目。

具备任务范围能力时，只分析本次有效范围内的待处理包，不能删除自动展开的必要依赖或调用方。无关历史问题可经独立的全仓诊断另列，不自动纳入本轮，也不宣称其证据仍有效。旧工具不能安全分离范围时保留已有成果并报告收口缺口；不得删分析条目、猜造 `--only`、手改账本或回退他人改动来绕过限制。

### 完成状态与证据

| 实际结果 | 可以报告的状态与动作 |
|---|---|
| 构建、测试或产物核验通过 | 只能证明对应工程验证；不能替代适用的受管收口 |
| `development-analysis-required` | 开发未完成：需要范围分析；退出码 0 不表示收口成功 |
| `development-planned` | 开发未完成：只是计划，尚需实际 apply 和成功核验 |
| apply 返回 `development-closed` 且退出码 0 | 已执行收口；核对包清单、版本、追加记录、检查/产物及当前最终输入，再判断开发完成 |
| 当前预览为 `nothing-to-close` | 当前没有待收口项；可复用仍有效的记录或说明不适用，不伪称本轮执行过 apply，不用它代替本次工程验证 |
| 带本次包选择的预览为 `task-development-current` | `readiness_scope=task`，只表示本次有效范围没有待收口项；全仓范围未检查，不据此宣称可以 release |
| 需要 apply 却未执行、非零退出、缺失/未知结果或输入已漂移 | 开发未完成：保留原始失败阶段和现场，给出阻断及继续条件；不能从版本文件变化推断成功 |
| 事务中断或仍有 journal | 开发未完成：按工具诊断核对并经受管 recover 恢复；有外部修改冲突时保留现场。`development-recovered` 仅表示恢复，仍须重新预览、分析和收口 |

本次开发完成需要：本次需求和必要验证满足、适用审查完成、交付物对应最终内容、适用的受管收口对最终输入仍有效。无关历史问题单列，不要求全仓清零。报告命令/收据、终态与有效范围，不创建自制完成证书。需收口但未完成时说明相关阻断；release 仍按累计范围另行核验，不能从任务完成推断可以发布。用户验收与桌面效果分别报告。

## 2. 项目特殊验证与可选准备

读取项目 AGENTS 指向的真实入口，保留项目自身的必要检查、构建和产物要求。项目检查清单不能由骨架维护自动创建或削减，检查失败或未完成不得宣称通过。

原有 development-checks.json 和 prepared 是可选发布候选准备，不等于子包开发收口。只有项目及本次任务明确要求时，才按实际受管能力读取 --development-status 或执行 --prepare-release；不将缺少 prepared 当成普通开发未完成。该旧准备入口不修改当前 VERSION，不提交或推送，也不能代替子包版本事务。

相关输入、环境或产物变化时，按真实影响更新证据；不得为匹配指纹改写旧通过记录。未取得的真实下游和 runtime 证据如实标注。

## 3. 与 Git 发布的边界

- develop 收口仅更新子包；release 仅更新主程序并公告正式发布以来的累计子包版本变化。
- 未完成收口的受影响子包阻止 release，指出补齐验证和升版的动作；release 不自动补跑 develop。
- 普通 git-sync 不主动升版，不以子包收口或 prepared 为前置。
- 新的子包收口门槛不扩大为全项目开发 JSON、全量回归、用户验收或 prepared 门槛。
- 本 reference 不授权安装、部署、提交推送、生产数据、账户或其他项目写入。
