# 规划模式

## 定位与边界

只分析，不写盘；仅要求计划不授权实施。用户随后明确开工时，交接现有计划与授权，不重复确认。

## 输入

以 `$ARGUMENTS` 为规划目标；为空时从当前用户请求提取目标和范围。

## 核心流程

1. 按公共 AGENTS 的澄清规则，先只读相关代码、配置、测试和文档；不调用写缓存或更新环境的入口。
2. 仅就会实质改变方案的未决项提问；其余已授权取证继续，不凭文件名猜实现。
3. 列出受影响的文件、类或函数；能定位时附行号。
4. 按 `P0 / P1 / P2` 编排编号任务，并为每项写明修改目标与验证方式。
5. 列出潜在风险、依赖、未知项和需要用户决定的分叉。
6. 交付计划、未决项与实施边界；不为结束流程强制追加开工选择题。

## 输出与验证

输出必须包含：现状依据、影响文件、分步任务、验证方式、风险与停止点。不得把尚未运行的检查写成“已验证”。

## 停止条件

- 缺少会显著改变方案的关键输入：说明缺口并向用户确认。
- 没有实施授权：保持只读。

## 禁止事项

- 禁止在呈现计划的同一回合顺手实施。
- 禁止用泛泛建议代替对真实代码的检查。
- 禁止把未验证推断写成确定事实。
- 用户未明确要求执行验证时，禁止在计划阶段运行完整回归、下游 fixture 或性能测试；只列入验证方案。只允许为消除当前事实分歧执行必要的轻量检查。
