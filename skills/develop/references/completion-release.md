# 子包收口与项目特殊流程

> 涉及项目自有子包，或项目声明结构化开发记录、发布准备及特殊收口流程时读取。
> 使用前核验 `package-development-v1` / `package-stability-v1`；开发验证与受管版本收口分别报告。

## 1. 子包版本收口

版本判级、两个基线、自动进入 1.0.0 的条件及证据边界统一见[版本生命周期合同](../../git-sync/references/schema4.md)，不另维护第二套规则。

1. 核对项目注册包、版本来源、实际输入变化及已有有效收口；无变化不升版，同一内容重复运行不重复升版。
2. 在已授权的开发范围完成适用验证与必要审计，复用仍有效证据；不把工厂全量检查套到其他项目。
3. 按版本合同运行 `develop --preview`、生成实际包分析、带分析预览后执行 `develop --apply`；工具对最终候选执行项目检查，逐包判断 0.x 是否达到稳定标准，不升级主程序 VERSION。
4. 核验版本、相关依赖/锁、收口记录及最终交付产物一致；写版本造成实际产物或验证影响时补齐对应检查。失败不留下已认证的半成品。
5. 交付子包版本变化、判级依据、稳定条件缺口及验证范围。主程序发布和用户验收分别报告。

当前工具缺少新能力时，明确报告“开发验证已完成 / 子包版本收口未完成”，保留证据并停止版本写入；不得调用旧 release、手改 manifest 或伪造新收据补齐。没有子包变化的任务不额外要求收口记录。

## 2. 项目特殊验证与可选准备

读取项目 AGENTS 指向的真实入口，保留项目自身的必要检查、构建和产物要求。项目检查清单不能由骨架维护自动创建或削减，检查失败或未完成不得宣称通过。

原有 development-checks.json 和 prepared 是可选发布候选准备，不等于子包开发收口。只有项目及本次任务明确要求时，才按实际受管能力读取 --development-status 或执行 --prepare-release；不将缺少 prepared 当成普通开发未完成。该旧准备入口不修改当前 VERSION，不提交或推送，也不能代替子包版本事务。

相关输入、环境或产物变化时，按真实影响更新证据；不得为匹配指纹改写旧通过记录。未取得的真实下游和 runtime 证据如实标注。

## 3. 与 Git 发布的边界

- develop 收口仅更新子包；release 仅更新主程序并公告正式发布以来的累计子包版本变化。
- 未完成收口的受影响子包阻止 release，指出补齐验证和升版的动作；release 不自动补跑 develop。
- 普通 git-sync 不主动升版，不以子包收口或 prepared 为前置。
- 新的子包收口门槛不扩大为全项目开发 JSON、全量回归、用户验收或 prepared 门槛。
- 本 reference 不授权安装、部署、提交推送、生产数据、账户或其他项目写入。
