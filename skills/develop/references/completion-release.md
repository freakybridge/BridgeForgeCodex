# 开发收口与发布准备

开发收口负责证明代码已经完成；summary 沉淀经验并按授权验收，git-sync 同步及发布。读取项目 AGENTS 指向的检查清单，不把某个工厂的检查套到所有项目。最终发布准备前，按 summary 的经验沉淀流程将本轮有价值的开发与排障经验写入 doc，并完成必要索引，避免验收时补写正文导致准备失效。

1. 完成项目要求的实现、当前版本构建和质量检查准备。存在未通过的必要项时报告阻断，不宣称开发已完成。
2. 项目使用受管 BridgeForge 时，先运行 `self-test --json`，确认 `git-sync-prepared-release-v1` 能力；旧工具可能忽略未知参数并执行同步，禁止试跑准备参数探测能力。不支持则报告需要升级，不退回手工发布。
3. 先检查自检是否提供 `git-sync-release-readiness-v1`；提供时运行只读 `git-sync --release-status` 并完整记录全部阻断。读取项目 `.codex/development-checks.json`，确认其中检查命令属于已授权开发范围；不擅自添加安装、部署或外部发布动作。缺少项目清单时，由主 Agent 阅读项目 AGENTS、构建与测试入口后，在已授权开发范围内配置项目自己的非空检查清单；不照抄工厂清单、不猜测命令、不把需要账户或生产数据的测试加入自动执行。检查清单归项目所有，骨架升级不得覆盖。旧工具仍按既有文件检查流程诊断，不试跑不支持的参数。
4. 处理接入、版本基线与配置阻断后，用 `git-sync --release-status` 获取当前输入指纹。已推送的误升版本仍是发布基线，不用本地降版或删已发布日志作为补救；经用户确认保留该基线并记录纠错原因。需要独立审计时先复核，再将真实审计结论与指纹保存为 audit JSON（schema、fingerprint、reviewer、verdict、summary）；不得自行代替独立 Agent 给出“passed”。
5. 用受管 `git-sync --prepare-release --message-file <消息文件>` 执行配置检查和目标版本构建；需要审计时同时传 `--audit-file <记录>`。消息按真实变更确定 SemVer 类型。准备写入 `.runtime`，不暂存、提交、推送当前项目，不预写工作区 VERSION。
6. 只有 `prepared` 收据与当前输入相符后，才能交付待验收。报告检查结果、条件忽略项、目标版本、准备记录、剩余风险；不得把准备耗时隐藏进“发布只需几秒”的承诺。
7. 准备后的 summary 记录文档按项目显式 record_documents 清单做轻量校验，不重新构建。源码、Skill、依赖、配置、未声明文档、检查清单或目标版本变化须重新准备；提交说明变化不必重复构建同一目标版本。文档结构通过不代表语义审计通过，验收仍依赖实际证据。

没有 BridgeForge 入口的项目沿用自身构建和质量工具，也必须给出可核对的检查证据。此流程不授权提交、推送或发布。
