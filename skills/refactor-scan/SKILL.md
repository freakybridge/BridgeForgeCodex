# refactor-scan — 重构候选扫描

## 定位与边界

从真实代码和调用关系识别值得实施的重构，供用户按编号选择。
扫描阶段不修改业务源码；选择条目与实施授权分别记录，遵守已有会话决定。
默认允许项目现有的定向测试和离线性能基准。用户要求纯静态时保持纯静态。
扫描、实施和发布的授权不相互推定；本 Skill 不提交、推送或发布。

## 1. 确定范围与取证入口

1. 复用用户指定的项目、模块、目标和预算；未指定范围时默认当前项目。
   读取适用 AGENTS、项目文档索引、实际入口、构建/测试配置及工作区状态。
   对大型项目先给模块概览，再沿相关调用关系深入；不能把抽样称为全项目穷尽扫描。
2. 识别生成代码、第三方资产和受管镜像。以事实源分析，记录传播目标，
   不将镜像重复计为业务重复。尊重项目保护区域和既有未提交改动。
3. 映射主要业务能力、规则与状态的拥有者、输入输出、直接消费者、
   依赖方向和外部副作用。静态 imports 只提供线索；查证注册、配置加载、
   动态发现、回调和外部契约中与候选有关的真实连接。
4. 在高成本扫描或验证前复用 confirm 的规模与预算口径；未安装 confirm 时，
   明确范围、执行上限和验证安排。只有实质影响结果的未知项才需澄清。

## 2. 识别并核实候选

| 目标 | 有效线索 | 成立条件与方向 |
|---|---|---|
| 高内聚、低耦合 | 职责混杂、共享可变状态、循环依赖、跨层调用、一个规则改动触及多个无关模块 | 指明独立变化原因、当前拥有者和真实调用方；提出能收敛职责或缩小影响面的边界 |
| 合并散落逻辑 | 同一业务规则重复实现、生命周期分散、重复转换或计算 | 核对输入、语义、单位、错误规则和生命周期；同一职责归一，不同业务语义保留独立 |
| 健壮性、可读性 | 丢失错误、资源清理不明确、复杂控制流、名称与职责不符、重复分支 | 给出受影响路径和项目现有契约；区分已证实缺陷、维护成本与待验证风险 |
| 性能 | 循环内 I/O、重复查询/计算、无用拷贝或分配、不必要的串行等待 | 查明入口、数据规模和调用频率；没有基线时只列性能候选，不承诺实测收益 |

1. 文件长、目录扁平、函数相似或抽象少均不足以成立。
   对每个候选查证直接调用点、配置、相关测试、失败路径及外部契约，
   主动寻找它不应重构的理由；不能证实的问题标成待验证，不写成已确认缺陷。
2. 比较最小改动与结构调整：说明合并、拆分、移动、抽取或保留现状的取舍。
   新抽象应减少真实重复或明确职责；不按固定框架强加分层、接口和设计模式。
3. 将多处症状归入同一业务问题，避免一个文件一条或多处重复报同一问题。
   仍可独立实施的动作拆成条目；跨条目依赖和互斥方案明确标记。
4. 区分保持行为的结构重构、改变错误/业务/接口行为的修复和性能优化。
   明确必须保留的接口、数据形状、配置、错误语义、状态转换和副作用顺序。
   行为变化单独标注，不能混入“等价重构”。

## 3. 定向验证与性能基线

1. 从项目已登记命令中选择能回答候选问题的最小检查，先确认启动路径、
   数据来源、输出位置和副作用。允许测试缓存与离线基准产物，不代表业务源码可写。
   测试会接触生产数据、外部服务、安装依赖或自动修复源码时，不在扫描授权下执行；
   改用已有离线入口或列明缺口。完整回归仅在项目强制或另有有效授权时执行。
2. 记录实际命令、环境、目标场景、断言和结果，注明既有失败及验证局限。
   检查未执行、工具缺失或命令失败时继续不依赖它的取证，不自动安装或修环境。
3. 性能使用已有离线基准或可复现的已有计时入口，记录数据规模、版本、构建模式、
   样本次数和时间/内存/吞吐指标。无适用入口时给出待测方案；扫描阶段不临时改业务源码。
4. “路径中存在重复工作”“测得该路径耗时”“确认性能瓶颈”分别判断。
   瓶颈结论须有耗时占比、调用频率或可复现对照等依据。
   重构后的收益由 develop 在相同场景与方法下复测；不把离线基准扩大为真实用户性能。

## 4. 交付编号清单

1. 读取[清单与交接格式](references/report-contract.md)，输出模块职责概览、
   实际覆盖范围、按优先级排列的候选表和决策所需的详细证据。
   编号使用 R01、R02 等，复查和交接保持原编号；撤销条目保留撤销原因，新增继续编号。
2. 依据实际影响、证据强度、预期收益和实施风险排序；严重度不等于执行顺序。
   不为数量凑候选；没有值得改的项时说明范围和证据，允许结论为无需重构。
3. 默认在对话内交付。用户要求保存时按项目文档布局写入当前主题并同步索引；
   无有效布局只暂停保存，仍可交付对话报告。不新建全局 refactor/plan 目录。
4. 报告明确已执行验证、待验证项、跳过范围、结构变化与待测收益。
   要求用户按编号接受、暂缓、拒绝或选择互斥方案，不将扫描报告当成实施授权。

## 5. 确认与 develop 交接

1. 复用用户决定；“选中 R03”只表示接受候选，除非已有实施授权。
   已明确“实施 R03、R07”的授权直接继承，不要求再批准相同范围。
2. 只对选中范围核对证据是否仍有效；代码、配置、契约或环境变化时复核受影响条目。
   新出现的独立问题另列新编号，不静默追加到已授权实施范围。
3. 将选中编号、授权依据、文件/调用方、目标归属、保持行为要求、预期收益、
   依赖顺序、基线、验收和剩余风险交给 confirm，沿用其规模与预算唯一口径。
   简单项可走 develop 的 S 路径，不强制补 M/L 卡；M/L 按项目布局维护唯一需求包。
4. 需求和实施授权齐备时交给 develop；不在本 Skill 内重复实现、验证和发布流程。
   环境未提供 confirm/develop 时输出完整交接材料并注明缺失能力，不虚构已调用。

## 停止与收据

关键业务语义、目标归属或外部契约不明，只暂停依赖它的建议与交接。
预算不足时保存已取得的结果与覆盖缺口，停止新增工作。
交付报告位置（如保存）、候选与用户决定、实际验证、未验证范围及交接状态。
