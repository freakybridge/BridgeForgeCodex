# summary — 总结与验收收口

## 1. 定位与模式

`$summary` 只基于当前上下文、完整可见对话和已经存在的事实源整理结果。无参数是阶段总结；
精确参数 `同意验收` 才授权收口当前交付。其他参数必须停止并展示这两种用法。

| 调用 | 模式 | 允许写入 |
|---|---|---|
| `$summary` | 普通模式 | 零写入；只输出阶段总结 |
| `$summary 同意验收` | 验收模式 | 当前交付既有需求卡或 Bug 的 `lifecycle`、`validation_status`、验收状态与收据 |

调用 `$summary` 本身禁止解释为用户验收。`同意验收` 不需要重复确认，但已知 blocker、未满足
条件或冲突收据必须阻止关闭并说明原因。

## 2. 输入与证据

- 当前上下文与完整可见对话中的目标、确认、决策原因、反馈和遗留问题。
- 当前交付已存在的需求、设计、计划、Bug、TODO 和文档索引；禁止为收口临时创建事实源。
- 本轮已经产生的测试、审计、Git 与 runtime 收据。禁止为了总结重新运行测试、build、审计或 smoke；允许只读 `git status` 和相关 diff。
- 缺少收据时标记“未验证”，禁止把静态配置、代码存在或推断写成成功事实。

## 3. 执行顺序

1. 锁定模式，区分已确认事实、推断、已完成、未验证、待验收和 blocker。
2. 读取对应流程：[普通模式](references/ordinary-mode.md)或[验收模式](references/acceptance-mode.md)。
3. 发现可长期复用的 Rule / Hook 候选或归档候选时，读取[建议与归档边界](references/deep-steps.md)。
4. 输出已完成变更、实际收据、未验证项、剩余风险和下一步；所有候选都标记“未执行”。

## 4. Rule / Hook 建议边界

- 只有完整可见对话中存在重复风险、稳定触发条件和明确受益范围时才提出候选；证据不足就不建议。
- 候选必须写明：问题、触发条件、建议承载者、预期硬闸或规则、与既有事实源关系、误伤风险。
- 每项候选必须标记：`等待用户采纳；未写入；未实现`。用户在本次调用中同意验收，不等于采纳建议。
- 采纳后也必须由其他开发方法单独确认范围、落盘和验证；`$summary` 不负责实现。

## 5. 用户结果

- 当前模式与一句话结论。
- 已完成事项、关键决策及原因、实际验证收据、未验证项、blocker 和下一步。
- 验收模式下列出实际更新的既有文档路径；普通模式明确“零写入”。
- Rule / Hook 和归档候选（如有），统一标记“未执行”。
- `git status` 与相关变更，并明确“未暂存、未 commit、未 push”；发布只由 `$git-sync` 处理。

## 6. 禁止事项

- 禁止创建、更新、移动或删除项目 `.codex/memory/`，也禁止调用其 writer、rebuild、lint、检索或统计链。
- 禁止直接写入 Codex 原生 `~/.codex/memories/`，也禁止把项目写入失败回退到原生 Memory。
- 禁止自动写 Rule、AGENTS、Hook、配置或测试；禁止把建议伪装成已采纳、已写入或已实现。
- 禁止普通模式修改任何项目文件；禁止验收模式扩张到当前交付未显式关联的记录。
- 禁止自动调用 `$archive-scan`、执行 `git mv`、更新归档索引、`git add`、commit 或 push。
