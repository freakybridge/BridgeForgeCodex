# summary 经验沉淀流程

> 三种模式都必读。普通模式的交付物是项目内可检索、可复用的经验文档；不结算交付。用户要求只读时仅输出内容。

1. 从当前可见对话提取值得保留的开发和排障经验：触发场景、现象、走过的弯路、已确认原因、有效解决办法、验证证据、适用边界与仍未解决的问题。只记录有信息增量的内容，不抄聊天流水账，不将猜测写成根因。
2. 阅读 `doc/README.md` 与当前主题已有文档，先去重。同一经验优先更新原文；当前 delivery / Bug 的复盘留在对应主题，跨任务可复用的技术经验放 `doc/3_reference/`，项目长期领域知识放 `doc/5_project_knowledgebase/`。按项目实际布局确定路径，不创建第二份持续维护的事实源。
3. 使用当前对话和已有收据落盘，区分已验证事实、推断、失败尝试和未验证项。缺少验证就如实注明；禁止为了总结重新运行测试、build、审计或 smoke。历史 Memory 只作补充，不能代替本轮证据。
4. 没有合适文档时可以新建主题明确的经验文档，新增路径时同步 `doc/README.md`；不为了形成文件硬凑经验。重复调用时只补充新事实和修正旧结论，内容已覆盖则复用已有链接。
5. 项目使用发布准备记录时，优先在最终准备前沉淀经验；准备后仍按授权写 doc。只读核对项目记录：显式声明的记录类 Markdown 经轻量校验后可复用产物，源码、Skill、配置或未声明输入变化须回 develop。不得自行扩大允许路径、自动重跑长检查，或以保留 prepared 为由只展示文本。
6. 普通模式不改需求、Bug 或 TODO 的验收状态；经验文档存在不代表问题已解决或用户已验收。规则建议与归档候选按 `deep-steps.md` 处理，不自动实施。

输出实际文档链接、最有价值的经验和未验证边界。无新增有效经验或用户要求只读时说明原因，不能把一次聊天回复称为“已沉淀”。
