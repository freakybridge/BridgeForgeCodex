# summary accept — 验收与 TODO

> 完成普通模式的经验沉淀后读取。accept 表示用户确认当前开发符合需求，不代表无关任务验收或推送授权。

1. 对照当前交付已有需求、实现结果和验证收据核对验收条件。不重新运行测试、构建或审计；有明确 blocker、缺失必要证据或冲突收据时说明具体缺口，不标为完成。
2. 更新当前交付可唯一关联的既有需求、设计、计划或 Bug 验收记录。条件满足才按项目合同写 lifecycle: completed、validation_status: verified；未满足则保留 active 和真实验证状态。新经验文档不能代替缺失的验收证据。
3. TODO 使用项目固定总表 doc/0_architecture/TODO-INDEX.md；先按 ID 或同一事项去重，沿用现有格式、编号和状态。没有总表且确有事项要记录时才创建，使用“编号 | 日期 | 内容 | 状态 | 关联文档”，编号从 TODO-001 递增，登记 doc/README.md。
4. 仅将本次有完成证据的已有 TODO 标为完成；未完成项保留状态，补充真实进展。将本次对话明确发现且未解决的问题追加为待办，附证据/线索和关联文档；推测改进不自动记账。已有详细文档是验收事实源，总表只保留短状态和链接，不复制维护完整验收正文。无关 TODO 不修改，不迁移历史待办。
5. 经验文档、验收记录和 TODO 写完后，项目启用发布准备时只读核对现有记录。项目显式允许的记录文档经轻量校验可以复用产物；源码、Skill、配置或其他开发输入变化则报告需回 develop，禁止为了 accept 补跑长检查或伪称准备有效。
6. 规则建议仍是“等待用户采纳；未写入；未实现”。已验收事项可列归档候选，但不调用 archive-scan，不移动文件。

输出实际修改的经验文档、验收记录和 TODO 链接；分别列完成、保留、新增的 TODO，无变动则说明。明确未提交、未推送。
